# 活动反馈提案的固件评审

评审对象：[activity-feedback.md](../protocol/proposals/activity-feedback.md)。评审依据为当前 `main/badge_state.c`、`main/badge.h`、`main/main.c`、`main/badge_ble.c`、`partitions.csv` 和冻结的 [protocol/v1](../protocol/v1/README.md)。本次只新增评审文档，没有修改产品源码、冻结协议、存档、构建产物或设备。

输入提案 SHA-256：`d34160eb1b7cda14d652c7c32c66b86abafe31ddb9485085779d8aa783fa9b15`。

建议在产品负责人确认动作/阶段和时效规则后再实施。提案方向可实现，但目前缺少真实返程语义、明确的历史基线规则和可执行的存档升级/降级策略，不能直接加字段后发版。

## 当前实现事实

- `cat_forest` 命名空间的 `state_v1` 是整个私有 `saved_t` 的原始 C 内存 blob，使用 `STATE_MAGIC=0x43415431`，严格校验读取长度等于当前 `sizeof(saved_t)`。其中保存宠物快照、全局事件 counter、队列 count 和最多 200 条 `{counter,timestamp_ms,blocked}` 事件。
- `saved_t` 内嵌 `badge_snapshot_t`。直接往该类型添加活动字段会改变 blob 长度或偏移，现有校验将拒绝旧数据；不能通过放宽长度检查或强制转换来“兼容”。
- 事件 ID 由硬件稳定的 deviceId 和持久 counter 生成。迁移必须保留 counter、每条队列事件和 blocked 标记，不能重新编号、重新生成宠物 UUID或清空未确认互动。
- 游戏存档和 NimBLE 安全记录使用各自的存储逻辑。当前 SC/MITM/bond 持久化应保持；迁移不能调用 `nvs_flash_erase`、整分区擦除、`ble_store_clear` 或用户配对恢复的 peer 删除路径。
- 当前分区为 `nvs@0x9000,size=0x20000`（128 KiB）、`phy_init` 和单个 factory 应用分区，没有 OTA 双槽回滚设计。活动扩展不应改变这些分区位置，也不能宣称已经具备 OTA 自动回滚。
- 固件未建立可信墙钟：v1 的 `updatedAtMs` 是状态修改时间，事件 `timestampMs=0` 明确表示未知。硬件具有 RTC 不代表当前软件已校时或验证。
- `acknowledged_events` / `snapshots_received` 只在 RAM 中观察当前运行的真实 ACK/接收路径，不是活动去重账本，也不能用于跨重启防重播。

主集成已报告目标构建和 21 项手势回归通过；本评审没有重跑构建或测试。这些结果不代表新活动提案已实现，也不代表真机 BLE、掉电或功耗验收通过。

## 需要先定案的语义

| 风险 | 建议约束 |
|---|---|
| `started/active/completed/cancelled` 缺少“返程中” | 主集成已核实当前手机流程是在真实成功结算后结束并回小屋。当前可显示“回家啦”的已完成结果；不能在 completed 后补播“刚出发→游玩→返程”。若产品需要返程过程，先在原生端增加并持久化真实阶段，再决定增加 `returning` 或明确的 stage 枚举。 |
| kind/action/location 尚未完整映射 | 给每个实际原生动作列出合法元组、进入/完成/取消条件及原猫可用反馈；逐项冻结封闭枚举。不能由 food+25 猜喂食，也不能由 location=forest 猜已在游玩。 |
| 同一 UUID 的字段和阶段可能被不一致地重用 | 同一 activity.id 的 kind/action 应不可改；location 是否允许路径变化要明确。拒绝已完成/取消活动重新变成进行中，除非有明确的新活动 ID。 |
| 可选字段与 v1“忽略未知字段”可能导致假同步 | 新旧双方先明确协商协议/能力。v1 返回 synced 只说明核心快照已处理，不能解释为 activity 已处理。未协商时发送 v1 核心状态，并明确活动画面不可用。 |
| 未知动作或无效活动的处理没有冻结 | 明确整条快照拒绝、错误 reason、以及原生是否另发核心快照回退；不能静默丢弃 activity 后宣称整项活动同步成功。 |
| 完成与游戏奖励可能分开写入 | 活动 completed、奖励/扣费、核心 revision、恢复记录由手机同一真实存档事务提交。吧唧只展示已提交结果，不自行补奖励或按超时结算。 |

## 保留 `state_v1` 的安全迁移路线

推荐新的核心+活动状态仍作为一个完整记录持久提交，以满足提案的原子可见性要求；使用独立新 key 做首次 copy-on-write，保留旧 key 作迁移检查点。以下步骤需要先用 fixture 和目标 ABI 验证，再写升级代码。

1. **冻结旧解码器。** 从当前已构建目标固定 `saved_v1`、`snapshot_v1`、`event_v1` 的布局、`sizeof`、`offsetof`、端序和 magic，生成带未绑定、已绑定、满队列、blocked、计数高值的真实布局夹具。旧解码器不能继续引用将来会增长的 `badge_snapshot_t`。host 结构布局通过不等于 Xtensa 目标布局已经验证。
2. **定义明确的 V2 记录格式。** 使用独立 schemaVersion、长度、校验信息和有界字段；优先显式序列化以避免继续依赖 C padding。完整记录包含原核心状态、原队列/counter、新活动和必要的展示去重标记。schema 版本和游戏 revision 是两件事；单纯迁移不增加游戏 revision，也不制造活动。
3. **只从有效 V1 构造。** 校验原长度、magic、UUID、数值范围、count<=200、counter、事件顺序和 blocked 后，在 RAM 中逐字段复制。初始 activity 为 none；历史展示基线设置为“需要新会话首帧基线”。迁移不得改变 petId、快照 revision/updatedAtMs、数值/金币、队列顺序、counter、已有事件 ID 或拒绝状态。
4. **写新 key，再启用。** 首次迁移写 `cat_forest/state_v2`，成功 `nvs_commit` 后读回并完成长度/校验/语义核对，才切换运行态。保留 `state_v1` 原字节，不先删旧 key，不用独立的 activity key 与核心状态分别提交后假定它们天然原子。
5. **给“V2 已启用”留下持久依据。** 在有效 V2 已提交并读回后，再写小型格式启用标记并验证；在这之前不接受新的 V2 游戏/队列写入或发成功确认。不能假设跨多个 key 的写入天然是一个事务。启动时有效 V2 优先；只有确实未启用 V2 且无 V2 记录时，才允许从有效 V1 首次迁移。
6. **失败保留现场。** V2 写入/commit/读回/标记失败时不覆盖 V1、不清空 bond、不发迁移成功，不把缺失/损坏当新用户。RAM 中的不可信字段继续隔离，错误页应可读且不能访问越界队列。已启用 V2 后若 V2 损坏或缺失，禁止悄悄回退到冻结的旧 V1，以免回退 counter 并重用 eventId；进入明确恢复流程。
7. **验证写入预算。** 在固定 SDK 上确认 blob 更新的实际掉电语义和空间需求。128 KiB 是整个 NVS 分区标称大小，不能直接当作可用余量；峰值要计入保留 V1、新 V2、更新所需空页、bond/CCCD 和垃圾回收空间。若单 key 更新的故障保证不满足验收，使用带 storageGeneration 的 V2 A/B 完整槽；不能拿仅游戏 revision 选最新，因为排队/ACK 不一定改变宠物 revision。

本轮只提出上述路线，没有创建新 key 或启用标记。正式升级前还需确认用户设备上实际运行的是哪份固件和分区表；历史报告或当前编译成功不能证明设备已有本项目 V1 存档。

**保留旧 blob 不等于可直接降级。** V2 启用后 V1 检查点会过期，刷回旧固件可能读取旧数值、丢失新队列、倒退 counter 并重用已被手机去重的事件 ID。回退必须由经过验证的转换器，把最新有效 V2 核心状态、全量队列/blocked、同一宠物和 counter 高水位导出为精确旧 ABI，再配套验证手机去重记录；或者在产品明确接受数据回退后执行单独恢复方案。仅恢复升级前 NVS 备份，也不自动解决手机已经确认过更高 eventId 的问题。没有这项验证时，禁止把旧二进制称为无损回退方案。

## 历史首帧和一次性反馈

建议采用“会话首帧静态基线 + 在线有效转换”，而不是收到 completed 就播放一次动画。

- 开机从 NVS 恢复后，所有活动只按“上次状态”显示。新连接/重连且能力协商完成后，第一条被接受的活动快照只建立当前静态基线，不播放离线期间缺失的出发、游玩或回家过渡。
- 只有建立基线后，实时收到并持久接受的合法活动转换，才产生对应短提示/轻量姿态。新活动首次看到的就是 completed/cancelled 时，只显示静态结果；没有看到出发不能补造旅程。
- 去重至少区分 activity.id 与一次性阶段。相同 id/phase 的新核心 revision 可能只是金币或其它数值变化，不能重复触发完成反馈。重复帧只重发同步确认。
- 一次性阶段的“已消费/展示高水位”需要持久保存，并在展示前提交，以保证至多一次。掉电发生在“标记已消费但还没画完”之间，可能漏掉一次视觉反馈；这是需要产品接受的取舍，不能同时承诺物理展示恰好一次且永不重播。
- 整体活动、游戏快照和展示标记采用同一完整记录语义；处理失败时不先画成功。手机获得快照持久确认与用户看到动画是不同证据，不要把 BLE 连接成功当活动已同步或已展示。
- 清除 BLE 配对记录不清活动基线/队列。新手机只有恢复同一宠物和真实存档才可继续；不通过重新配对绕过 pet_mismatch。

这会有一个诚实的体验边界：用户离线完成整个出游后再连接，吧唧显示最新完成结果，不补播假装实时发生的全过程。当前手机真实成功结算的“回家啦”结果可以沿此规则实现；真实返程过程须先增加原生阶段。

## 活动失效与不可信时钟

现提案只有 id/kind/action/phase/location，无法确定进行中活动何时失效。`updatedAtMs` 不能代替现在，单凭“接收后再跑一段固定动画”会让旧活动在每次重连后续命。

建议在新修订契约中选择一种明确方案：由原生依据实际已提交阶段及其计时源，提供有界剩余租约；或提供稳定的阶段失效时间和新鲜的发送时钟元数据，并说明时钟有效性。具体字段名、最长时长、允许延长条件需要负责人冻结，本评审没有擅自添加 wire 字段。

- 吧唧当前开机只用单调计时减少剩余租约；不因系统墙钟回拨改变结果。冷启动后原 uptime deadline 已无效，不能继续使用。
- 同一活动同一阶段的重复帧、其它数值引起的更高核心 revision、重连旧帧都不得重置或延长原租约。真正延长活动必须有契约允许且可验证的原生阶段更新。
- 若使用绝对失效时间，手机应在实际串行发送时计算新鲜度，不重放积压的旧序列化包；还要界定 BLE 传输延迟/时钟误差的保守扣减。不能只比较旧 expiresAt 与旧 sentAt 后从接收时重新计满。
- 时钟未知、租约过期、未知阶段或没有新鲜基线时，停止持续动作，静态显示“上次出游状态/请在手机查看”，保留数据并等待新快照；不要自行改成 completed/cancelled，也不要发奖励事件。
- completed/cancelled 的短提示显示时长可用本地单调计时，但提示超时不是游戏状态转换。静态结果的保留周期另由产品确定。

## 最小迁移与活动验收

以下先用旧/新真实格式 fixture 做故障注入，再在用户批准的单板升级中复验。无需新建账号、云服务或敏感传感器权限。

| 场景 | 必须看到的结果 |
|---|---|
| 有效 V1：未绑定/已绑定/空队列/200 队列/blocked/高 counter | 迁移前后核心字段逐项相同，未确认事件 ID/顺序/blocked 相同，下一个新 ID 不重用 |
| 错长度、magic、UUID、count>200、counter 倒序/越界 | 原 NVS 字节保留，可读错误页，安全 RAM 状态，无越界、无自动初始化替代 |
| 在 V2 set_blob、commit、读回、启用标记各步骤断电/失败 | 重启只采用有效且已允许使用的格式，不发假成功，不回退到过期 V1；原快照、队列、bond 可核对 |
| V2 启用后更新过快照/新增或确认过事件，再试降级 | 旧固件直接降级被交付流程阻止；受控转换保留最新核心值与 counter 高水位，否则明确判失败 |
| 升级前已配对手机重连 | bond 无需自动删除，仍要求加密认证；待确认事件按同 ID 重放且手机不重复结算 |
| 初始历史 completed、初始历史 active、离线完成后重连 | 静态基线，不补播出发/返程，不重复奖励；未知或过期 active 不无限动作 |
| 在线真实开始→合法阶段→完成/取消 | 手机存档、revision、实际协议帧和吧唧短提示对应；取消无奖励；已完成结果可显示“回家啦”，无虚构返程阶段 |
| 重复帧、相同活动更高核心 revision、逆序/非法阶段 | 不重复一次性反馈；无合法转换就不改活动；错误明确可恢复 |
| 展示高水位提交前后断电 | 已消费阶段不重播；允许遗漏一次视觉反馈，游戏结果和队列不丢失 |
| 无时钟、时间回拨/大跳、重启、旧帧延迟、重复租约 | 保守静态回退，不续命、不凭过期自行成功结算 |
| 分片/UTF-8/最大消息/未知动作 | 2048 字节含换行限制不变；拒绝路径不改存档；新旧能力回退不假称活动已同步 |
| 单板真实显示/触摸/掉电/电池 | 圆屏 safeR212、文字对比、低亮度和动作结束后的静止状态可核对；真实耗电与恢复记录单列，host/AVD 不替代 |

进入实施前最少需要负责人确认：先支持的真实动作与阶段（尤其是否新增返程过程）；历史首帧静态/至多一次反馈的取舍；活动租约与无时钟回退规则。确认后冻结独立修订契约、目标 ABI 迁移夹具和受控升级/回退说明，再修改两端。全量 PRD 目标继续保留，此评审没有批准删减。
