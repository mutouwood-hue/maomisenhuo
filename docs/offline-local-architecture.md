# 无云依赖的手机—吧唧架构与剥离分析

## 1. 本轮结论与权限边界

用户最新说明是本轮需求依据：“不需要所谓的云”“修正后的 HTML 基本是正确内容”。当前基线为项目根目录 `小橘电子宠物.html`（SHA256 `3e1b68b6dcef89ce6003961e0abb41354785443bd0427b83ed70f7589fd8af53`）及用户后续修正；旧 PRD 的云主控、账号、云同步假设已被该决定取代。PRD 暂不可访问不再构成本地还原工作的前置阻塞。

本轮只读审查源码并保存分析。未改手机 UI、主工程逻辑、旧源码、用户存档、权限或凭据；未运行依赖安装、网络请求、构建、测试、BLE 连接或刷写。文中“剥离/替换”全部是待实施方案，不能理解为已删除或已迁移。

**建议基线组合**：修正后的完整 HTML（包含 social-v7）负责体验和原玩法；复用旧 Capacitor 容器中合适的安全区、返回、导出、手势和本地 BLE 实现；原固件源码到达后优先保留其驱动、导航和资源。当前新 Kotlin/固件候选中的持久化、去重、失败不结算等修复只作为可移植材料，不把新候选或旧版后台面板当产品基线。

旧归档 `original/game.html` 是较早快照（SHA256 `c4f872d0bf8a899cf93a6aa877c13c5a5090e1f592729500bd2ef476205e9952`），缺少修正版 social-v7，life/grad 脚本也不同。直接采用它会丢掉用户修正，不能用“旧包保留原 HTML”代替逐版对齐。

## 2. 云依赖在哪里

完整清单、文件哈希和拟处理方式见 `legacy-review/cloud-dependency-map.json`（22 项）。关键关系如下。

| 层 | 实际依赖 | 拟处理方式 |
|---|---|---|
| 构建入口 | `scripts/build.mjs` 总会注入 companion-prelude、companion.js、社交后台样式 | 后续隔离构建从入口排除云扩展；保留原脚本顺序与必要 mobile/native/BLE 层 |
| 登录与生命周期 | `companion/main.js` 恢复账号会话、15秒轮询、绑定云面板、包裹 store 方法、替换 `__pgLife` provider | 本地协调器替代；删除账号依赖不能只隐藏按钮，否则 provider 覆盖与回调仍存在 |
| 存档权威 | CloudSave 云 revision/CAS、pull/push、远端 save import、账号 owner | 完整本地家庭存档 + 本地修订与事件账本；不得自动恢复远端或覆盖原存档 |
| HTTP/埋点/AI/更新 | ApiClient、TelemetryOutbox、LifeSync、AiAdapter、UpdateUploader | 首个离线产品入口不装载这些网络职责；保留历史数据，禁止假成功响应 |
| 设备同步 | BadgeSync / scheduler 从后台取得 challenge、authGrant、签名时钟/猫/生活对象；事件交后台结算后才 ACK | 分离可复用的分包/CRC/会话隔离，与需要重新设计的本地信任和持久确认 |
| 遇见与图鉴 | 旧 social panel/controller/client 从后台读取朋友/资产/谱系/奖励及签名挑战 | 用修正 HTML 的遇见和图鉴；仅接入本地领域与真实通信适配，不保留后台式操作表单 |
| 传感与授权 | 用户会话、后台 consent/eligibility、环境签名授权、后台位置服务 | 本轮全部保持默认关闭，只有明确模拟规划；不能用本地假“资格通过”绕过旧门禁 |

`src/mobile/*` 的此次定向搜索未发现依赖 companion API；`src/ble/client.js`、protocol.js、BleLocalPlugin 本地传输也不要求账号。它们具备单独复用的条件，但仍需接正确 HTML 和固件版本。

## 3. 本地权威与数据边界

### 手机：原玩法的本地规则与完整存档

- 原 HTML store 保留猫咪家庭、activeCatId、成长、照料、出游、道具、愿望、毕业等规则。币、经验、图鉴和奖励由一次完成的本地事务结算；动画完成不单独发奖。
- 不能把当前新 `PetStore` 的单猫结构直接覆盖原家庭存档，也不能依据后台 DTO 把本地图鉴改成云资产列表。存档 ID、猫 ID、社交 ID 映射必须持久、可核对，不能截断哈希后忽略碰撞。
- 一份本地导出包需要包括原完整游戏存档、`pg-social-v1` 等原社交记录、版本、设备关联、事件去重账本及校验。备份/恢复沿用原体验并补校验，不要求账号。若从 `com.catforest.app` 与 `com.warmpaws.town` 两个不同应用迁移，必须先分别备份、对比；应用ID不同不会自动共享存档。
- 选择 Native 事务存储或 IndexedDB 等容器实现之前先核对旧源；目标是保留原 store 契约。`localStorage` 单键写入不能当成跨游戏与社交多个 key 的原子事务。若继续原多键存储，需要可恢复的写前日志/提交标记，不能只靠多次 setItem 后发 ACK。

### 吧唧：保留原 UI、缓存与可靠离线事件

- 保留原完整 23 屏与手势、引导、省电及真实资源，不因取消云而缩减为文字页。
- 设备产生的真实互动先可靠保存，才表示“已记录”；未被手机持久确认的事件断连后保留。手机收到同事件只结算一次；写入失败不发终态 ACK，拒绝事件保留原因，队满不伪成功。
- 手机提交本地规则结果后发确认与新快照；设备先持久保存确认/快照再更新已同步显示。双方重启、丢 ACK、重复包都不能重复奖励。
- 断连时展示上次确认状态及待同步量。设备若要离线独立修改数值，必须有明确可重放事件规则；不能设备与手机各改一份后最后写入者覆盖。
- 切猫或换手机需要明确、可撤回的本地选择；不能把 `pet_mismatch` 当成自动清空旧数据的理由。

## 4. BLE：保留已证实的接口家族，新增本地能力要双端明确协商

原设备备份内同时找到旧 App 的 service/RX/TX 三个 `e7f1a000-1c9b-4a7e-9d2f-3b8c5e6f7a00/01/02` UUID。旧本地帧固定 20B，BJ magic，序号与 opcode 相关 ACK。HELLO 与 GET_STATE 只读握手和按钮 START_LOCAL 分开。该证据不能证明全部扩展已就绪或源码与烧录版本完全一致。

新候选 `7b2e…`/NDJSON/LE bonding 与此不同，不能混接。原设备当前运行 `orange_cat_pet` v1 / ota_0；“连接 App”不能直接解释成云账号绑定失败，也不能仅凭字符串确定它等哪个命令。

可复用：串行 GATT write-with-response、同序号同 opcode 应用 ACK、generation 防旧回包、断连取消、超时不自动重放变更、20B分包与对象 CRC。**CRC 只防传输损坏，不是身份认证。**

不能直接复用为无云方案的部分：旧对象中后台签名、provision、账号 session 与后台终态 ACK 的含义。不得用零签名、假 grant、跳过验签或本地假 HTTP 成功把链路强行接通。

待旧固件源到达后：

1. 对照 HELLO/GET_STATE/START_LOCAL 的实现，确认连接页、引导、离线本地模式的真实条件；不以审查为由现场发变更命令。
2. 核对 opcode6 capabilities、对象读写与验证入口，确认哪些仅传输、哪些依赖后台。旧 App `decodeHello` 还严格要求 capabilities=15，不能单端随意扩位。
3. 设计有明确能力位/版本协商的本地同步扩展（暂不分配数值），写清本地会话、关联猫、快照 revision、持久事件序号、去重与错误码。旧客户端/固件不支持时明确停在可用旧本地模式，不降级冒充成功。
4. 本地物理确认与传输认证保留独立边界；采用设备配对或本地密钥方案要依据旧实现与用户流程选定，本轮不生成密钥、不修改安全设置。
5. 任何需要新固件的改变先离线构建/验证，仍遵守原双备份、原分区和精确写入授权。取消云不等于获得刷写授权。

当前 `protocol/v1/README.md` 的“long-term PRD cloud primary storage”是已过时的产品假设，不再作为新需求；该历史冻结文本本轮未修改，不能继续据它要求云主控。它的本地去重/先保存再 ACK 原则可独立保留。

## 5. 遇见与图鉴：用原体验，分清原型演示和真实对端

修正 HTML `social-v7-js` 已具备附近/暗号/节奏/九宫格/遇见码、朋友/礼物/图鉴、家具、联机蛋及本地成长规则；`__pgSocial` 导出原领域入口，数据保存在 `pg-social-v1`。`dex()` 已展示拥有/见过品种、愿望印章、成长、第一次、地区、家具等。旧后台 `localCollection()` 只是其子集，不能替换完整图鉴。

原 `BroadcastChannel('pg-badge-air')` 明确用于同浏览器多窗口模拟 BLE 广播；NPC 路过与随机 RSSI/估算距离也是原型机制。保留这些体验时仍要标明 NPC/演示，不能把它当作两台真吧唧已互认。真实蓝牙的 RSSI 也不能承诺精确3米测距。

`PGM1` 遇见码在本地解析、10分钟过期和 nonce 去重，但其短 hash 校验不是可信签名或全球身份认证。它可作为原玩法的离线交换格式起点，不应继续套后台签名挑战来“完成”原体验。

真实遇见适配层应把设备扫描/实际输入/对端确认交回原 UI 和原规则：本地有独立 encounterId、双方临时随机数、输入记录与确认/取消状态；只在满足对应玩法完成条件后调用一次原结算。失败/超时/取消不发成功动画或奖励。双方断连后不能伪称全局原子完成；以两侧持久回执和恢复步骤区分待对端确认与已完成，不引入“中心服务器已确认”的虚构状态。

设备到设备采用何种真实链路尚未确定。当前“手机 central—吧唧 peripheral”不会自动提供两台吧唧互传；蓝牙、二维码或其它局域传输选择需先看旧固件现有能力。保留原敲击/九宫格/扫码的呈现与手势，不用后台式表单替代它们。

## 6. 无云不等于可以启动原 HTML 所有权限

- 地点、环境、语音、儿童信息继续按本轮约束只做默认关闭的模拟规划，未真实采集。不能因为去掉后台 eligibility 就本地返回“已合格”。
- 原 HTML 内还有可选场景生成请求（blocks-v6 的外部模型调用）、定位、按住说话、环境麦克风和扫码相机入口；发布本地构建时必须按用户授权范围门控，不能只移除 companion 网络代码就称无外部请求。
- 保留原积木渲染器和已内置配方；没有模型服务时直接使用这些原资产，不伪造“生成成功”。本轮不新增 API、凭据、模型服务或真实语音。
- 原“voice”字段不全是录音：社交性格吐槽、合成提示音等不能按关键词一并删除；区分表现层、麦克风读取和外部模型。
- Native 导出桥使用 `fetch(blob:)` 读取本机导出，这不属于云请求，需保留。Android 的 INTERNET 是否可去掉需以容器本地资源加载验证后决定，不做关键词式删权限。
- Android 11及更旧 BLE 扫描的系统定位权限要求与真正采集 GPS 是不同边界；不能一刀切移除导致蓝牙不可用，也不能借 BLE 授权启动真实定位。测试手机 Android16 走附近设备权限，当前不申请新权限。

## 7. 推荐实施顺序与后续验收

1. **基线冻结**：保留当前备份、候选、隔离旧源和修正HTML。旧固件未到前先完成差异清单，不重写驱动/导航，不自动切应用ID或导入存档。
2. **本地壳清理**：呈现线程在独立副本按修正HTML保留全体验；构建入口排除云面板/API/provider覆写/账号恢复/上传与OTA，仅接必要原生适配。本轮没有实施这些变更。
3. **原本地连接**：旧固件核对后，用匹配旧协议构建端到端握手/状态/明确本地开始流程；先保留原体验，记录实际版本与状态，不混用新旧协议。
4. **本地同步扩展**：双端冻结清晰协议后实现快照、持久事件、幂等确认和本地备份；优先移植已有可靠处理，避免换一套玩法或将后台伪装成本地服务。
5. **真实遇见接入**：复用 HTML 交互与图鉴，逐一换掉演示传输，真实能力未就绪的流程保留明确不可用，不以NPC结果冒充真人互认。

后续需要另行执行的验收（本轮未运行）：

- 无网络且无账号时冷启动、照料/出游/图鉴/保存/重启恢复完整可用，无登录/云页面阻断；仅真实设备功能可能请求必要附近设备权限。
- 网络观测无外部 HTTP/WS/埋点/模型/OTA请求；允许容器本机资源和 blob 导出。旧配置、账号残留或缓存不能启动会话恢复/后台采集。
- 真手机/真吧唧握手、旧程序本地进入条件、同步与断线重连有版本/设备/截图证据；用实际固件而非预览替代。
- 事件提交前/后杀进程、丢 ACK、重复传输、快照乱序、切猫、队列满、写盘失败均不重复扣币/发奖，不丢队列，不自动清数据。
- 图鉴、遇见的原HTML页面/暗号手势/成功失败/返回/取消逐项比较；原 NPC、真实对端、未知状态保持区分。
- 导入导出覆盖完整游戏与社交记录，恢复前保留现状；不同应用ID及旧数据迁移必须单独核对，不自动合并或清除。

## 8. 仍需输入与责任

唯一关键技术输入是旧吧唧源码及其构建版本映射，尤其本地模式、扩展对象验签/持久队列、原资源。用户已决定不需要云，不再就该产品方向重复提问。

呈现线程继续负责手机 UI；集成者负责协议/设备/统一构建及后续真实验收。本轮没有向主工程写入任何剥离实现。


## 旧固件到达后的确定结论（2026-10-15）

归档 `baji-firmware-src.zip` 已安全隔离（7519项、277.40MB展开，无危险路径/链接；跳过4个vendor.git元数据），只读源在 `legacy-review/firmware-source/baji-firmware`。三份实证报告：firmware-build-review.md、firmware-ui-review.md、firmware-protocol-review.md。前文“等待旧固件”已由此更新，后续待的是能力/基线选择与实际设备验证，而非用户重复提供同一源码。

- classic与V2共享e7f1三UUID，但classic为type/length/payload社会协议，V2才是BJ20。不能按UUID判可控制，更不能据此确认当前烧录分支。手机独立adapter必须实际HELLO验证。
- V2基础1..5无provision可运行；START_LOCAL进本地教学，不代表认证，GET_STATE只含设备UI状态。私有事件读取、PET/LIFE/TIME及精确ACK依然需后台签名session，不能说无云同步已完成。
- classic具规格驱动页面/真实cat3d渲染器和原动作，V2只有10种screen enum及两套不透明24帧猫小循环。两者都不能整套替代修正体验；优先复用驱动、资源及可验证交互。
- 经典main自动NVS erase、部分事件延迟保存/队满丢旧；V2引导/face仅RAM及部分release误触问题均需隔离修复。分区默认factory表不符设备，M2表与原备份七项相同也不授权启用rollback或刷表。
- 已在 `artifacts/local-ble-adapter/` 实现独立纯Java+JS基础桥，SDK35 javac与15项Node fixture通过，交手机owner接入。尚未接设备，不开放假快照/好友能力，不执行刷写。
