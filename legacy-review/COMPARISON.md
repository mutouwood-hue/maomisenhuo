# 旧 Android 源码与修正后 HTML 对照

本轮为只读源码对照，日期 2026-10-15。需求以用户最新说明和项目根目录 `小橘电子宠物.html` 为准：不需要云账号、云主控、云存档；手机与吧唧需要真实连接。旧 PRD 中相反的假设不再作为要求。

**建议以修正后 HTML 的界面和玩法作为恢复目标，选择性复用旧 Android 容器、手机适配和真实传输代码。旧包整体不是合格基线。** 保留 HTML 的原交互比再次设计界面更合适，但旧包新增的“遇见与图鉴”“云与设备”和 BLE 测试面板明显改变了信息组织。WebView 本身不能说明体验好坏。

## 证据与范围

- 归档 `warm-paws-town-android-src.zip`：1,698,130 字节，SHA-256 `483e025f4b437642e082d39bef927c24c97f07047f2e5e4963da7ab8476be6e4`。
- 安全检查 180 项，共解压 6,340,551 字节，未发现不安全路径、链接或重复项；解压至 `legacy-review/source/warm-paws-town`。未发现需跳过的敏感文件名不等于已证明源码不存在秘密；本轮未提取凭据。
- 复核解压文件与 ZIP 的逐文件内容：零差异。没有修改旧源码、主工程、手机数据或固件，没有安装依赖或向网络上传。
- 旧包附带的历史验证文档仅是历史记录。本轮没有取得旧 Android 运行截图，没有浏览器、真机或 BLE 新验收。以下视觉差异来自 DOM、CSS、资源和交互代码，不冒充截图审计。用户提供的原 HTML 手机图只支持首屏视觉基线，不能证明三个二级面板实测通过。

## 一、三个重点区域

### 1. 遇见：从宠物场景变成跨模块操作表单

| 对照项 | 修正后 HTML | 旧 Android 新增面板 | 建议 |
|---|---|---|---|
| 入口和导航 | 右侧功能轨分别有遇见、图鉴；进入同一社交浮层的指定页签 | 更多抽屉插入“遇见与图鉴”，另有“云与设备”和 BLE 测试入口 | 保留原两个入口和页签定位，不要求先去设备后台页完成一串操作 |
| 主画面 | 雷达、当前小猫像素形象、附近猫卡片、信号圈、可遇见状态 | 合并长对话框，首先显示云回执、登录、隐私资格，再列发现开关、受控场地、二维码、能力和挑战操作 | 复用原雷达和 `petImg` 猫素材；显示“未连接 / 正在寻找 / 发现小猫 / 等待对方 / 成为朋友” |
| 操作组织 | 附近、好友、礼物、世界、图鉴、设置六页；每页围绕一件事 | 八个 section 混合朋友、礼物交换、联姻、图鉴、环境、日记、OTA；静态模板共 39 个按钮、11 个 select、8 个 input | 把配对技术步骤收进连接流程，把好友操作留在具体猫卡或详情；环境、更新不进入遇见主页 |
| 交互反馈 | 邻近猫高亮、距离提示、见面/赠礼的专门浮层、未读点 | 手动“读取能力 / 发挑战 / 提交证明 / 查询结果”，会话 ID 和后台状态直出 | 保留真实确认，但由状态机自动执行协议步骤。只让用户确认对象、玩法和结果；错误原地恢复 |
| 返回与关闭 | 自有 `sc-hub`、`sc-meet` 浮层、遮罩关闭和 Escape | 新增 `<dialog>` 有关闭、焦点返回、扫码停止；原生返回接线只覆盖旧扩展浮层，未包含新增 v7 `sc-hub`/`sc-meet` | 容器复用时补统一浮层栈，先结束最上层临时流程，再返回房间；关闭扫码同时释放摄像头 |

源码依据：HTML 6500–6526、6903–6935、7469–7497、7588–7590；旧 `src/social/view.js:1`、`src/social/panel.js:12–72`、`src/companion/main.js:131–132`、`src/native/bridge.js:72–93`。

注意真实能力边界：HTML 用 NPC、同浏览器 `BroadcastChannel` 和遇见码演示社交，不能把这些写成已实现真实 BLE 双机遇见。原文“约 3 米”是产品表达，RSSI 无法保证精确距离。应保留视觉和流程，以真实设备发现、能力和双向确认替换适配器；没有真实来源时显示空态或明确试玩来源，不伪造附近玩家。

### 2. 图鉴：不仅是换颜色，旧版缩减了内容模型

| 对照项 | 修正后 HTML | 旧 Android 新增图鉴 | 建议 |
|---|---|---|---|
| 布局与素材 | 进度条、猫像素图网格、拥有/见过/未发现三态、稀有轮廓、印章卡、谱系箭头和性格刻度 | `showList` 文本列表，混排品种、愿望、毕业、云谱系 | 直接复用原 `dex()` 和相关 CSS、像素猫生成，保持卡片层次 |
| 品种和状态 | 九品种，包含稀有后代；拥有与见过分开 | `localCollection` 硬编码六基础品种，仅 `isCollected` | 从原 catalog 派生，保留三态，不能用六项布尔列表覆盖原数据 |
| 收集范围 | 养成事件、怪行为、交换卡与锁定、联机后代、友谊印章/暗号/缘分、地域、毕业谱系、性格和技能 | 本机基础品种、已领取愿望、毕业；可选云谱系 | 所有 HTML 已有类别逐项保留；未完成真实硬件接线的来源显示实际状态，不整块丢掉 |
| 文案 | 愿望标题、宠物名和来源叙事 | `GOALS={}`，愿望缺映射时直接显示内部 ID；资产也显示 catalogId/assetId/status | 复用 catalog 的用户文案；ID、JSON 和协议状态只进入折叠诊断 |
| 离线能力 | 本机收集数据即可打开 | 本机基础集合可看；云刷新另有登录要求，图鉴埋在长表单后段 | 图鉴直接离线打开，所有进度来自已持久保存的本地事实 |

源码依据：HTML 6547–6556、7530–7545；旧 `src/social/controller.js:1–17`、`src/social/panel.js:37–57`、`src/social/view.js:1`。未截图，不能据此断言旧版具体像素间距或屏幕末行可达。

### 3. 云与设备：按最新需求退出云概念，保留连接体验

旧面板标题为“真实数据与云存档”，静态模板包含 18 个按钮、9 个 input：后台地址、账号、密码、邀请码、迁移、拉取、推送、生活采集、后台定位、上传埋点、设备绑定与补传，末尾还有摘要 JSON。另一个 BLE 测试对话框有 11 个按钮、2 个 select，显示 MAC、RSSI、HELLO、GET_STATE、PING、SET_FACE 和 JSON 状态。即使共享奶油色和圆角，这种任务组织仍要求用户操作实现细节。

建议产品入口改为 HTML 风格的“我的吧唧”或“连接吧唧”：主卡显示宠物形象、设备名、连接状态、电量（仅有真实读数时）；状态决定唯一主要动作“寻找吧唧 / 连接 / 重试”。设备物理确认进入独立一步；断开、重新配对、版本放在详情。连接完成返回房间，设备连接不能依赖用户一直打开测试对话框。底层命令、地址、摘要和传输计数保留为按需诊断，不占玩家主流程。

源码依据：旧 `src/companion/main.js:18`、`src/companion/panel.css`、`src/ble/panel.html`、`src/ble/panel.js:34–66`。`panel.js` 当前关闭 BLE 对话框会主动断连，所以仅重新排版不足以满足上述体验。

## 二、去云需要解开哪些依赖

隐藏入口不够。旧代码把“账号身份、云存档权威、设备签名授权、生活采集、社交资格”联在同一流程中；去云应作为明确的离线架构变更，不是文案替换。

| 层 | 当前依赖/风险 | 离线剥离方向 |
|---|---|---|
| 启动与界面 | `main.js` 构造 ApiClient、读取旧 session；表单登录、云恢复、云同步入口 | 不挂载云面板，不恢复网络会话，不初始化云定时器；保留原 HTML 入口和本地存档 |
| 游戏写入 | `wireGameMutations` 包装照料、愿望、家庭、毕业等方法，触发延时云 push；15 秒调度和隐藏页面 push | 移除包装器及相应调度接线；游戏仍通过原 store 校验和持久保存，不因去云重置进度 |
| 设备连接 | 低层 BleLocalClient 不要求账号；高层 `requireBadge()` 先 requireLogin | 将连接会话交给独立本地设备服务，生命周期不绑定设备面板或网络 session |
| 设备授权 | BadgeSync 的 challenge、binding、authGrant、signed objects 由后台签发 | 选定并验证固件协议后采用其本地配对/授权能力。不能简单跳过签名、伪造 grant，或把旧安全协议改成“默认成功” |
| 设备事件与结算 | drainOne 上传后台，接受返回 save 后再签名 ACK；ActiveEvents 依赖 session 与 cloud activeCatId | 本地单一权威保存完整家庭，按设备事件 ID 去重，持久化成功后回执；失败保留设备队列。不要把网络成功条件直接删掉而丢失事务顺序 |
| 社交与图鉴 | SocialClient 通过 HTTP 请求朋友、发现、证明、礼物、交换、联姻；SocialDeviceBridge 要求云设备 session | 图鉴本地派生；遇见接真实设备发现和双向确认。资产交换、后代等需要离线双端事务设计与固件能力验证，不能宣称删后台后自动可用 |
| 生活与环境 | 采集、同意、可信资格、撤回墓碑、摘要、环境签名、AI 日记都调用后台 | 按 HTML 和实际设备能力保留本地设置及明确授权；保留“未知”状态与撤回先停采集原则。服务器型功能先从产品流程移出，不请求用户填写后台 |
| 更新与网络 | OTA 清单、制品下载和签名依赖后台；AI 和埋点有独立请求路径 | OTA 与日记不再挂在遇见页。是否保留离线签名制品升级另立任务；不因去云关闭固件签名校验 |
| 历史数据 | `companion:<userId>:`、cloud metadata、pending撤回与备份、家庭本机存档是不同状态 | 本轮不删不改。后续先导出备份，规定本地归属和兼容迁移；撤回未确认不能自动重新开启。云字段退出运行路径，不等于批量清空历史数据 |

关键代码：`src/companion/main.js:29–100,124–139`，`badge-sync.js:29–45`，`src/social/client.js:1–69`，`src/social/panel.js:21–28,91–118`，`prelude.js:1–14`。旧 prelude 还会重写原 HTML 授权设置、关闭 demo、清理旧 provider key 槽和旧遥测地址；不应直接搬入新的 HTML 基线并假定只是容器适配。

离线目标可明确为：HTML 视图与原玩法 → 本地完整家庭存档/事件事务 → 设备适配器 → 已确认的固件协议。网络账号、云资产、云签名不在照料、图鉴、连接的必经路径。此处是实现建议，尚未完成离线社交或协议改造。

原 HTML 自身也残留“正式版由云端校验一机一密”等旧说明（7224），与用户最新无云要求冲突，应在实现时一并校正；这不构成继续建设云平台的需求。

## 五、建议落地顺序与验收

1. 冻结旧包与当前候选，记录本地存档备份；修正后 HTML 作为唯一视觉/玩法来源。先移植完整 social-v7 视图和资源，避免重新生成按钮表单。
2. 隔离旧 companion 云入口、网络调度和 store 包装器；设备 transport 单独接线。先确认实际固件属于哪套协议，再接物理确认与状态读取。
3. 明确本地家庭 store 的唯一写入权、设备事件去重和持久回执；用断连、超时、重复回执和重启恢复验证。原有云安全边界不能用假回执代替。
4. 遇见、图鉴、设备分别验收：原入口定位正确；图鉴所有类别和稀有三态存在；设备主流程不出现地址/账号/协议命令。未接真实能力的部分提供可理解的空态。
5. 取得 390×844、360×640 与大字号实际截图/操作证据：完整猫脸，动作目标避开底部通知和至少 48dp 触控坞；单通知槽，抽屉/玩法期间暂停房间手势和粒子，关闭后恢复一次；愿望末行可达；扫码关闭释放摄像头；系统返回逐层收起。

主工程先前两个待核项已在本轮源码检查中看到修复：MainActivity 主帧 onReceivedError 现清 ready/care/feedback 并提供点击重试（157–165）；closeLife 失败后不再用通用 message 覆盖详细失败（1073–1088）。此处只表示代码存在，不替代错误注入和生命周期实测，也不把已修复项重复列为开放缺陷。
