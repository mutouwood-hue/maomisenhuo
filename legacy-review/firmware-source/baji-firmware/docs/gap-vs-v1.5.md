### 新增的积木场景要不要上板？

**不需要（现在）**。`blocks-v6-js` 是 Web 原型的 3D 场景搭建：自述为「组件库 + 配方校验 + 搭建」，只用自建存储键 `pg_bk_v1`（配方缓存）与 `pg_bk_key`（API Key），**完全不碰存档 `pixel-cat-pet-v1`、不动 `version:2` 的 schema**；整块里 `xp` 出现 **0 次**；新增的 14 个 DOM id 与旧文件零冲突；唯一网络调用是网页直连阶跃星辰 API，而文档 §5.4 自己说明「原型里的积木场景工坊为测试方便由网页直连」，正式版 Key 不下发到端侧。

若将来要上板，那是**新增功能的欠账**（对应文档 §5.4 / Q11，需要端侧 3D 场景搭建与配方存储），**不是既有规则的失效**。

## 3. 渲染口径冲突（§7.4 明文 vs 我们的实现）

这是本轮**唯一一处文档与代码的正面冲突**，且它早在 v1.3 就存在（见 §1 末）。

| 维度 | v1.5 §7.4 要求 | 我们的实现 | 取证 |
|---|---|---|---|
| 光栅化 | 分条带渲染，每条 **466×32**，颜色双缓冲 59.6KB + 深度 29.8KB，两条交替渲染/送屏 | **全屏一次**，无条带、无双缓冲、无 DMA 重叠 | `cat3d.c:688` 遍历全部 336 面；`:770-774` 背景填充；`:791-815` 光栅化。`main/`+`components/` 里 `strip\|条带` 零命中 |
| 深度 | **16 位深度缓冲** | **画家算法**：平均深度 + 插入排序 | `cat3d.c:729-747`（`depth` 只是排序键，`:119`）；全仓无 z-buffer 数组 |
| 贴图 | **4bpp 调色板**，每套 32KB，6 套 192KB，全资产约 201KB | 原始 **RGB565**，每套 131,072 B，6 套 **786,432 B** | `cat_model.h:6-8`；6 个 `*.bin` 实测各 131,072 B |
| 分辨率 | 桌面态 466 全屏 30fps / 互动态 233 半分辨率×2 ≥24fps | **300×300**（=90,000 px，面板 466×466 的 **41%**），单一 30fps 目标 + 自适应降档（下限 12fps） | `main.c:41 CAT_VIEW_SIZE 300`、`main.c:551 cat_view_set_target_fps(30)`、`cat_view.c:210-231`；**无半分辨率/放大路径** |
| 局部刷新 | 每帧只重画「**本帧 ∪ 上帧**」矩形 | 缓冲区按并集清背景 ✅，但**交给 LVGL 的失效区域只有本帧** ❌ | 见 §4 |
| 光照 | 每面一个法线 | **逐面** Lambert → 32 级 LUT ✅（粒度一致） | `cat3d.c:712-727`，`CAT3D_SHADE_LEVELS 32` |
| 双核分工 | 核 0 渲染、核 1 跑 BLE/业务/LVGL | **无任何核绑定** | 全仓 `xTaskCreatePinnedToCore` 零命中；唯一建任务 `net_link.c:687` 未绑核；渲染跑在 LVGL 定时器 `main.c:101` 里，与 UI 同线程 |

### 这对 `docs/render-route.md` 的结论有影响吗？

**没有推翻，但需要补一条边界说明。** render-route.md 的结论是"继续 cat3d、否决 PCAT"，且**明确声明该结论只建立在风险上、不建立在性能上**（`:12`、`:345`）。§7.4 的条带/深度缓冲是**技术规格要求**，不是性能证据，所以三条风险理由（flash 不是约束 / cat3d 已验证已接线 / PCAT 无 C 代码且无板不可验证）一条都没被动摇。

但从风险记账的角度要分清三件事，否则后人会误读成"选 cat3d 就自动满足 §7.4"：

1. **4bpp 可在 cat3d 内闭合**——只需换贴图格式，不需要换渲染器（render-route.md `:396` 已经这么写）。且 flash 不是约束：现占 8 MB `factory` 分区约 10%。
2. **深度缓冲也可在 cat3d 内闭合**——给 cat3d 加真 z-buffer，300×300 约 180 KB，PSRAM 够用（render-route.md `:324` 已给出这条最小修法）。它顺带解掉 render-route.md §6.1 记录的那个**golden 测试永远抓不到**的失效模式：加服饰方块后画家算法可能排序错乱，而参考实现 `tools/firmware-ref.mjs` 用的是同一个画家算法，两者会同错。
3. **"466×32 条带 + 双缓冲 + DMA 重叠"是结构性改造**——要把全屏一次渲染改成条带化调度，这是唯一一条真正伤筋动骨的。按 render-route.md §6.1 自己的触发条件，**应在拿到板子后用真机数据决定**（`ref.js:277-278` 的双条带缓冲假设从未在真机验证过，render-route.md `:378` 已记录）。

文档侧也**没有**"必须用 PCAT"的硬条款：Q7（3D 渲染库）状态仍写「待确认（上板对比后定）」，§7.4 的成本模型自标「粗估…上板实测后校准工具包里的系数（待实测）」。

## 4. 圆屏 vs 矩形布局：吧唧 UI 的根本性偏差

> 这一条由用户直接指出：「你做的吧唧页面没参考我给的演示 html，我给的演示里面都是环形的 UI，你还是按照 PC 端简单的重放」。下面的量化证实是我的补充取证。

**权威来源**：`_ref/notion/吧唧渲染参考.html`——演示里 `#scr` 就是圆屏（`.screen{border-radius:50%;overflow:hidden}`），并且有显式遮罩只统计圆内像素：

```js
const c = 233;                                  // 圆心 (232.5, 232.5)
for (y…) for (x…) if (dx*dx + dy*dy <= 233*233) mask[…] = 1;   // 可见区 = r ≤ 233
```

把现有 `main/ui/pet_ui.c` 的布局常量代入同一个遮罩公式：

| 现有元素 | 中心 | 到圆心距离 | 判定 |
|---|---|---:|---|
| rail 磁贴 1（衣柜） | (20,75) | **264.5** | 圆外 |
| rail 外角 | (0,34) | **305.7** | 圆外 |
| 照料按钮 row0 第一颗 | (42,407) | **258.3** | 圆外 |
| 照料按钮 row1 第一颗 | (42,445) | **285.4** | 圆外 |
| 照料按钮 row1 最后一颗 | (383,445) | **260.4** | 圆外 |
| 状态栏左端 | (4,16) | **314.8** | 圆外 |
| 状态栏右端 | (462,16) | **315.5** | 圆外 |
| 小猫（canvas 中心） | (232,184) | 48.5 | 圆内 ✅ |

**结论**：左侧 rail 与大部分照料按钮在真机圆屏上落在表壳底下，玩家**看不见也点不到**。而 `main/` 与 `components/` 里 `circle\|mask\|233\|ring` **零命中**——没有任何圆屏处理。这不是"少做了一个功能"，是**版式前提错了**。

**演示里的环形 UI 是什么**：`faceSeg` 三档表盘（只有小猫 / 24 小时时间环 / 时间环 + 心动），`drawRing()` 画外圈 r=218 宽 18 的主人行程、内圈 r=200 宽 6 的小猫行程、r=188 刻度、r=230 心动红点、r=218 现在白点、`HH:MM` 在 `(233,420)`。交互是**拖动=倾斜、轻点=挥爪**，没有九宫格按钮。

**文档侧其实也没描述"九宫格"**：§7.5 把吧唧 UI 层写成「LVGL 状态、气泡、**设置**；3D 控件合成」，§7.4「3D 互动」只列 倾斜视差 / 看向你 / 触摸反馈 / 遇见反应。我们却做了 9 个照料按钮 + 4 个 rail 磁贴——那是 **App 的控制面**；而文档要求的 `设置` 我们**零实现**。

**修正后的评分**：§2 表里「UI 层 ⚠️」与「24 小时时间环 ❌」要按本条重新理解——时间环是**这个圆形界面唯一的核心元素**，它缺席正是版式退化成矩形布局的原因。

## 5. 本轮发现的可判定缺陷：增量渲染残影

§7.4 要求局部刷新用「本帧 ∪ 上帧」，而代码**只做到一半**，这是一个**真实缺陷**（不是文档口径问题）：

1. `cat3d.c:749-774`（步骤 4）把背景重绘在 **`prev_*`（上一帧）** 矩形上——缓冲区这一步是**对的**（注释也写 "union of the last two frames"，但代码只用 `prev_*`）。
2. `cat3d.c:777` `dirty_reset(c)` 之后才光栅化本帧，于是 `:818-826` 的 `c->dirty_*` **只剩本帧**。
3. `cat3d.c:831-840` `cat3d_dirty_rect()` 返回的正是这个**本帧**矩形；调用方 `cat_view.c:267-271` 只按它 `lv_obj_invalidate_area()`。
   而 `cat3d.h:126-129` 的文档注释**声称返回"union of the previous and the current frame"** —— 头文件与实现不符。

**后果**：猫曾经占过、本帧不占的那条区域，缓冲区里已成背景，面板上仍是旧像素，且**永远不会被重绘** → 残影/拖尾。

**为什么一直没被发现**：golden 测试 `tests/host/test_render.c:102` 每帧前都调 `cat3d_invalidate_all(c)`（强制整屏），**从不走增量路径**。这条路径此前 **100% 无测试覆盖**。

> 处理状态见文末「本轮变更」。残影**在真机上是否肉眼可见**属未验证（板子接着但没做这项观察；见 §7.2）；但"代码层面的并集缺失"是可判定的，这一条已由回归测试锁定。

## 9. 本轮变更

### 9.1 上板实测：主机测试抓不到的缺陷（重要）

板子（`ESP32-S3-Touch-AMOLED-1.75C`，`COM3`）实际上是接着的。首个镜像上板后**立刻暴露两个缺陷**，而它们**在宿主机测试和编译里全都是绿的**——这类缺陷正是本报告 §7 一直在强调的那一类。

**① `pet_save_load()` 的 8192 字节局部数组撑爆 main 任务栈**

反汇编取证（我独立复现过）：`pet_save_load` 的函数序言是 `entry a1, 0x2030`，即 **8240 字节栈帧**；而 `CONFIG_ESP_MAIN_TASK_STACK_SIZE = 3584`。栈指针在开机第一次调用时冲出栈底，且**报出来的却是隔壁任务的账**：

```
***ERROR*** A stack overflow in task esp_timer has been detected.
Backtrace: ... 0x403892ce:0xa5a5a5a5 |<-CORRUPTED
```

因为被破坏的是相邻任务的金丝雀，而 `esp_timer` 的 tick 回调只做一次 `lv_tick_inc`，根本不可能溢出。修法：缓冲区提升为文件级 `static`（成本落进 `.bss`），并加 `_Static_assert` 把"缓冲区小于格式"变成编译失败。修复后 `pet_save_load` 帧降到 48 字节，真机启动日志为 `loaded 95 bytes` → `restored 1 cat(s), 120 coins`。

> **为什么主机测试看不见**：PC 给测试进程的栈以 MB 计；`test_pet_save.c` 那 74 项全绿，而那个数组就在被测文件里。我在报告初版里把"无板"当成了前提，因此**没能预判这类缺陷**——这是本轮我最该修正的判断。

**② BLE 的 GAP 事件此前没有任何接收方 → "会面过一次之后永久不再广播"**

`ble_gap_adv_start(..., NULL, NULL)` 与 `ble_gap_disc(..., NULL, NULL)` 都传了 NULL 回调，而 `gap_event` 只挂在 `ble_gap_connect` 上。于是本机作为 **peripheral**（两块板子见面的常态）时，连接事件、MTU、断开、扫描结果**全部无人接收**。

我从 NimBLE 源码独立验证了那两条机制性论断，均**成立**：

- `ble_gap.c:3287-3288` 与 `:3557-3559`：连接事件同时投递给**全局监听器**与**该连接自己的回调**——所以两处都挂同一个 handler 会**执行两次**（`on_link_state` 双发、`start_advertising()` 双调）。这解释了为什么修复时把 `ble_gap_connect` 的回调一并改成 NULL 是正确的。
- `ble_gap_adv_finished()`（ADV_COMPLETE 的产生点，`:1335`）的调用点是 `:2099/:2105`（显式停播）、`:3817`（广播超时）、`:2617`（扩展广播路径）、`:3357`（定向广播超时）——**没有一处是"对端连接"。** 所以 `s_link.advertising` 在整个连接期间保持 `true`，断开分支的 `if (!s_link.advertising) start_advertising();` 永远不成立。实测证据是直白的：手机连上来读完 GATT，串口**一行相关日志都没有**；而走 central 路径（挂了回调）日志正常。

即修复前**近场社交每开机只能用一次**，之后板子静默失联、而屏幕上一切正常。

**③ 我独立复核了镜像一致性**：真机启动日志里的 `ELF file SHA256: 8937d69f7…` 与 `D:\orangecat-build\orange_cat_pet.elf` 的实测 SHA-256 `8937D69F70737FAC…` **前 8 字节完全吻合**，确认烧进去的就是这份源码构建出来的镜像，日志不是旧固件的残留。
