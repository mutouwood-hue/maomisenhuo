# 帧率预算

用户明确纠正过一点：**真机是 AMOLED 屏，帧率是硬要求**。这份文档说明这个要求具体被翻译成了什么数字，以及为什么。

先说结论：**面板不会被整块刷新，所以 466×466 的物理尺寸不是渲染负担。**真正决定帧率的是"每帧要往屏幕推多少字节"。当前固件的重绘单位是两套：猫层自己的脏矩形（猫 3D 的唯一热路径），和面板画布上**变化过的元素盒子**（由 `main/ui/badge_ui_plan.c` 决定、`main/ui/badge_ui.c` 执行）。

本文只写性能与重绘预算。**分层顺序、过渡动画、已知偏差（三条实打实的 + 一条经核算不成立的更正）、以及宿主测试的覆盖边界见 [`render-route.md`](render-route.md) §8–§10**，不在这里重复。

---

## 1. 五个表面，别混起来

面板是 **466×466 AMOLED**（`BADGE_SCR_W/H`，`main/main.c` 的 `_Static_assert` 钉死），驱动的刷新周期是 15 ms（`CONFIG_LV_DEF_REFR_PERIOD=15`，`sdkconfig.defaults`）。上面叠着五个表面：

| 表面 | 尺寸 | 格式 | 内存（字节） | 说明 |
|---|---|---|---|---|
| 猫层 full | 466×466 | RGB565 | 434,312 | `badge_cat.c` 用 `cat_view_create(parent, BADGE_SCR_W, BADGE_SCR_H)`；desk/comp/aod 用它 |
| 猫层 half | 233×233 | RGB565 | 108,578 | 互动态（`modes.play.res = 233`）；首次进入互动态才创建，之后保留 |
| 面板画布 face | 466×466 | ARGB8888 | 868,624（848 KiB） | PSRAM；圆盘、环、弧、按钮、图标全部画在这里 |
| 合成画布 comp | 466×466 | ARGB8888 | 868,624（848 KiB） | PSRAM；气泡 / toast / 边缘环 |
| 过渡快照 trans | 466×466 | ARGB8888 | 868,624（848 KiB） | PSRAM；**首次切屏时才分配** |

（三张 466×466×4 的 PSRAM 表面、各自的字节数，出自 `main/ui/badge_ui.c` 顶部的内存段落；`233×233×2 = 108,578`、`466×466×2 = 434,312`、`466×466×4 = 868,624` 是按尺寸算出来的。`848 KiB = 868,624 B`。）

三个画布的尺寸**没有**"只画猫的范围"这种优化：猫层就是整块面板大小，因为 `badge_cat.c` 把屏幕的 `cat.dist/ox/oy` 映射成相机（见 `badge_cat.c` 顶部的投影公式），猫在屏上的位置由相机决定，不由画布边界决定。（`main/ui/cat_view.h` 顶部仍写着"画布只取猫的屏幕范围"，那是旧的、与现在的调用点不一致的注释，照代码读。）

**只有猫层会按动画帧率重绘。** face 画布只在元素盒子变化时重绘（§4.2），comp 只在合成层出现时重绘，trans 只在切屏的 220 ms 内存在。

## 2. 实测：466×466 视口上一帧要重绘多少

数字来自 `build/host/cat3d_dirty_test.exe`（源码 `tests/host/test_cat3d_dirty.c`，默认视口 `VP_DEFAULT = 466`）。本会话直接运行，输出：

```
viewport            466 x 466
frame 1 published = 312x358@77,53
frame 2 published = 312x375@77,49
frame 2 own bounds = 188x375@139,49
buffer diff (true change) = 312x375@77,49
rect before the cat leaves = 312x358@77,53
rect after the cat leaves = 312x358@77,53
rect after invalidate_all = 466x466@0,0
29 checks, 0 failure(s)
```

两个姿态是 yaw 90 与 yaw 180（`YAW_A/YAW_B`），刻意选成互不包含。逐项读法：

| 数字 | 含义 |
|---|---|
| **312×375@77,49** | 第 2 帧**发布**的脏矩形（上一帧 ∪ 当前帧，再夹到视口），= 117,000 px |
| **188×375@139,49** | 猫**自己**这一帧画到的范围，= 70,500 px |
| 312×358@77,53 | 第 1 帧发布的矩形，也是"猫离开后必须擦掉"的矩形 |
| 466×466@0,0 | `cat3d_invalidate_all()` 之后（全量重绘路径） |

两点必须说清楚：

1. **发布的是并集，不是当前帧的范围。** `cat3d_render()` 清上一帧的矩形、但早期只发布当前帧的矩形，于是猫拖着自己的残影走。测试对每一帧独立算出帧缓冲的真实差异，并要求发布的矩形覆盖它。
2. **这些数字是宿主机的实测，不是板端实测。** 它证明的是"重绘区域有多大"这个代码级不变量；真实 NimBLE/LVGL/面板在环时的耗时不能从这里外推（§9）。

于是每帧推给面板的字节数（RGB565，每像素 2 字节）：

| 情况 | 像素 | 字节/帧 |
|---|---|---|
| 猫的实测最坏脏矩形（312×375） | 117,000 | 234,000（228.5 KiB） |
| 猫自己的范围（188×375） | 70,500 | 141,000 |
| 全量重绘其中一个 466×466 表面 | 217,156 | 434,312 |

**关键数字：猫的一帧最多重绘 117,000 像素，不是 217,156。**

### 2.1 猫一帧走多少个面（逐面剔除，不是按部件剔除）

模型的**逻辑**规模是 336 个面、448 个顶点、14 根骨骼、56 个部件（`components/cat3d/data/cat_model.h` 的 `CAT_FACE_COUNT` / `CAT_VERT_COUNT` / `CAT_BONE_COUNT` / `CAT_PART_COUNT`）。生成的数据里每个部件确实带一个模型空间 AABB（`bound_min` / `bound_max` / `first_face`，`cat_model.h`），**但渲染器一个都不读**：`components/cat3d/src/cat3d.c` 里这三个字段的引用次数是 **0**，它每帧按 `CAT_FACE_COUNT` 遍历**全部**面（`cat3d.c` 的 `for (int fi = 0; fi < CAT_FACE_COUNT; fi++)`），只做法线逐面背面剔除，外加一个逐面的视口范围快速排除。所以 AABB 是预留给将来的数据，不是当前生效的剔除手段。

（`render-route.md` §4.4 引用的就是这条：接上 AABB 是"可做但非关键路径"。）

## 3. 带宽账

| 场景 | 每帧字节 | @30 fps |
|---|---|---|
| 猫的实测最坏脏矩形 | 234,000 | 6.7 MB/s |
| 猫自己的范围 | 141,000 | 4.0 MB/s |
| 全屏重绘（只在 `invalidate_all` 路径） | 434,312 | 12.4 MB/s |
| 过渡快照的 220 ms（每帧整屏） | 434,312 | 12.4 MB/s |

CO5300 走 QSPI，按 4 条数据线、40 MHz 估算是 **20 MB/s 量级**（**估算，未在真机测过**）。所以猫的最坏情况约吃掉 **1/3** 带宽；整屏 30 fps 会吃掉六成，那才是会卡住的场景——脏矩形机制把它避开了。

过渡期间是例外：`trans` 快照与下面的图层同时被移动/合成，220 ms 内每帧都是整屏级的合成，这是切屏而不是稳态。

### 3.1 切屏时"只有结果、没有过程态"——已知缺陷，未修好

真机上滑动表盘看不到过渡动画，只有跳变。原因是**切屏那一帧的 face 全量重绘太慢**，不是 `trans` 没做：

`badge_ui_rebuild()` 在离开一屏时先给旧屏拍快照（`ui_transition_snapshot()`），然后**同步**重绘整个 face 画布。这次重绘期间 LVGL 任务被占住，等它返回时 220 ms 的滑动窗口早就过完了，`badge_ui_transition_frame()` 只在最后一帧把新屏放到位——看到的就是跳变。

真机插桩（`esp_timer` 包住 `badge_paint_clear` 与 `ui_paint_elements`，逐个元素计时）实测一座带 24 小时环的表盘：

| 阶段 | 耗时 |
|---|---|
| `badge_paint_clear()`（整幅 466×466） | 121 ms |
| `ui_paint_elements()` | **2,452 ms** |
| 其中单个最贵的元素 `BE_DAYRING` | 2,450 ms |
| 该元素内单个最贵的 span（`rin=209 rout=227 deg=360`） | 570 ms |

已修的部分：360° 整环那条 span（上表最后一行）加了逐扫描线解析快路径，候选像素从 207,025 降到 13,013（16×），**像素级完全等价**（868 项 paint 断言 + 2,932 项 frame 断言原样通过）。但它没有让重绘变快——剩下的开销是圆弧 span 逐候选像素的着色，见下。

剩下的开销根因：ESP32-S3 只有**单精度** FPU，而 `bp_span_paint()` 的着色路径全程用 `double`（`sqrt`、除法、`bp_span_in_window` 的多次乘加），每次运算是 softfloat 库调用。实测每个候选像素约 1,660 周期。两次尝试把它降到整数都没成功：double 预筛 5.16 s → float 预筛 3.87 s → 提升常量后的 float 2.81 s → 纯 int32 2.97 s（都在同一台机器上测）。真正的修法在算法层：`bp_stroke()` 把一条圆弧切成**每度一个 span**（`steps = ceil(|span|)`），座标盘一次重绘就有 731 个 span、每个都走一遍逐像素着色。要治本得让整条不透明弧一次扫完（角度窗口逐扫描线解析求解），不要再切成一度的块——那是画笔模块的重构，不是参数调整。在没做那件事之前，**切屏的滑动过程态在带 24 小时环的画面上仍然看不到**。

## 4. 让帧率成为保证而不是期望的四个机制

### 4.1 猫的脏矩形

`cat3d_dirty_rect()` 返回**上一帧与当前帧绘制区域的并集**（夹到视口）。`main/ui/cat_view.c` 只把这一个区域交给 LVGL（`lv_obj_invalidate_area`），所以合成器推的字节数就是 §2 那张表。这不是优化，是正确性要求——只失效当前帧的话，猫转身时旧位置的像素会留在屏上（`tests/host/test_cat3d_dirty.c` 的 29 项检查就是这条不变量）。

整块画布重绘只发生在 `cat_view_invalidate()`（例如全量重绘路径）和"这一帧什么都没画"的兜底分支。

### 4.2 面板画布的部分重绘（这是新的重绘权威）

`main/ui/badge_ui_plan.c` 回答一个问题：**上一帧到这一帧，哪些元素的绘制输入变了？** 它返回一个盒子列表（上限 `BADGE_UI_PLAN_MAX_EL = 32`），`badge_ui.c` 只清这些盒子、并且只重画与盒子相交的元素。所以状态弧动一个点，代价是一条几百像素的带，而不是 868,624 字节。

这个模块不碰 LVGL（宿主测试用 `tests/host/lvgl_plan_stub/lvgl.h`），正是为了让"只重画哪些盒子"这件事可以被 PC 上的测试驱动，而不是靠看截图。它的宿主阶段 `tools/suite/04-frame.cmd` 与测试 `tests/host/test_badge_ui_plan.c` **都在树里**（本会话复核过），测试里也断言了部分重绘的预算（变化盒子的面积和）；每个 UI 模块被什么覆盖、什么没被覆盖，见 [`render-route.md`](render-route.md) §10。

### 4.3 三条独立的节拍

| 环节 | 周期 | 配置 |
|---|---|---|
| LVGL 刷新 | 15 ms | `CONFIG_LV_DEF_REFR_PERIOD`（`sdkconfig.defaults`） |
| 猫的重绘 | 每模式目标帧率 | `badge_fsm_fps()` → `badge_cat_layer_tick()` → `cat_view_set_target_fps()` |
| 应用定时器 | **10 ms（100 Hz）** | `APP_TICK_MS`（`main/main.c`） |

三条互相独立：猫重绘慢一拍不会拖住 LVGL 的 15 ms 刷新，触摸也不受渲染影响。

按模式的目标帧率来自规范（`badge_spec.json` 的 `modes.*.fps`，`badge_cat.c` 里以 `BADGE_CAT_FPS_PLAY 30 / COMP 12 / DESK 30 / AOD 0` 兜底）：

| 模式 | 目标 fps | 渲染分辨率 |
|---|---|---|
| 桌面充电态 desk | 30 | 466 |
| 互动态 play | 30 | 233 |
| 陪伴态 comp | 12 | 466 |
| 待机常显 aod | 0（不渲染） | — |

**`APP_TICK_MS` 为什么是 10 ms 而不是 20 ms**：交互规范按真实经过时间判定 tap（`tapMaxMs`）、swipe（`swipeMinPx` / `swipeMaxMs`）和长按（`longPressMs`），20 ms 的 tick 会把 150 ms 的长按量化成 140 或 160 ms。定时器本身不是渲染节拍——渲染节拍是上表的猫帧率。

### 4.4 自适应降速（保住交互的底线）

`cat_view_update_rate()` 在每次重绘后比较实测耗时与预算（`main/ui/cat_view.c`）：

- 预算 = 帧周期的 **3/5**（`CAT_VIEW_DUTY_NUM/DEN = 3/5`）；
- 超出 → 帧率降 2，未超出且有余量（`frame_us * 2 < budget`）→ 升 1；
- 下限 **12 fps**（`CAT_VIEW_MIN_FPS`），上限 = 目标帧率。

上限而不是硬编码，意味着降速后能自己恢复；下限 12 保证"渲染偶尔超预算"不会退化成"触摸无响应"。没有这道闸，一次超预算的重绘就会吃掉整个帧周期，下一个 tick 立即到来，队列越积越多——帧率崩到个位数，而触摸是同一个线程处理的，一起卡死。

固件的验收线写在 `app_perf_line()` 的注释里：**规范 PERF 节的预算是 ≥ 24 fps**；日志里 fps 低于它，就该同时看 cat_us 和 dirty。

## 5. 已做但属于"保险"的两项

| 措施 | 防的是什么 |
|---|---|
| **128 KB PSRAM 贴图缓存**（`cat_view_create()` 里的 `cat3d_set_texel_cache()`） | 贴图在 flash，经 cache 读取，而光栅化器按随机顺序取纹素；cache miss 落在最内层循环里，表现为帧时抖动而不是均值上升——而抖动才会打破帧率保证。把当前品种的贴图整体复制进 PSRAM 后读取延迟稳定。失败时打印 `no PSRAM for the texel cache; textures will be read from flash`。 |
| **热状态放内部 SRAM，帧缓冲放 PSRAM** | `cat_view.c` 的分配器按 64 KiB 阈值分流：大于它（帧缓冲）走 PSRAM，小于它（每像素都在碰的着色表、每帧碰的骨骼矩阵）走内部 SRAM。 |

如果日志出现贴图缓存那条警告，说明 PSRAM 没配好，先查 `CONFIG_SPIRAM_MODE_OCT`——那是配置错误，不是帧率调优问题。

## 6. 真机不达标时的调整顺序

按"效果/代价"排序：

1. **降各模式的目标帧率**：`badge_spec.json` 的 `modes.*.fps`（→ `badge_spec_data.c` 重新生成），或 `badge_cat.c` 的 `BADGE_CAT_FPS_*` 兜底值。24 fps 对这类养成游戏够用。
2. **放宽自适应闸门**：`cat_view.c` 的 `CAT_VIEW_DUTY_NUM/DEN`（现在是 3/5）或 `CAT_VIEW_MIN_FPS`（12）。这改的是"什么时候降速"，不是"每帧多贵"。
3. **确认 PSRAM 与主频真的生效**：`CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y`、`CONFIG_SPIRAM_MODE_OCT=y`、`CONFIG_ESP32S3_DATA_CACHE_64KB=y`（都在 `sdkconfig.defaults`，但生成的 `sdkconfig` 会覆盖它，用守卫脚本核对而不是只看 defaults）。
4. **最后才降猫的渲染分辨率**：`badge_cat.c` 的 `viewport_res()` 现在只有互动态走 233，其余走 466；把桌面/陪伴态也降到 233 等于降清晰度，代价最大。

`CAT_VIEW_SIZE` 这个常量已经不存在了，别再按它调。

## 7. 怎么看实时数字

固件每 5 秒（`APP_PERF_MS`）由 `app_perf_line()` 打一行常驻日志，**每个数字都是量出来的**：

```
I (…) app: PERF mode=play fps=28 cat_us=17 dirty=117000 px heap=71K screen=3 q=0
```

（格式取自 `main/main.c`；上面这行的具体数值是示例，**当前固件没有在本会话里上板采样过**，不要把它当实测值。）

| 字段 | 含义 |
|---|---|
| `mode` | 工作模式（desk/play/comp/aod/off） |
| `fps` | 猫的**实际生效**重绘率（自适应之后的值，不是 tick 频率） |
| `cat_us` | 上一帧猫光栅化的滑动平均（毫秒） |
| `dirty` | 猫脏矩形的**像素数**（不是 KB，也不是整屏） |
| `heap` | 内部 RAM 剩余（KiB）——这块板先耗尽的通常是它，而不是 PSRAM |
| `screen` | 当前屏幕编号 |
| `q` | 待上行的 8 字节事件条数 |

**这一行看不到的东西**：face 画布这一帧重绘了几个盒子、transition 的合成开销。要看盒子，读 `badge_ui_plan.c` 的返回值或它的宿主测试；要看过渡，读 `badge_ui.c` 的 `badge_ui_transition_frame()`。

旧的屏幕右上角读数 `渲染ms 帧率 合成KB` 已经不存在了——它属于被替换掉的那套 UI（`main/ui/pet_ui.c`，已删除）。

## 8. 板端实测（历史记录，观测点已不存在）

这一节是**历史**，保留是因为它是这个项目唯一一次真机采样的记录。**它测的是被替换掉的那套 UI 的猫画布（300² 矩形版式、320² 圆屏版式），不是当前固件**；当时的观测点是已删除模块自己的日志行（`I (7309) pet_ui: PERF 17ms 28fps 29k`，`pet_ui.c`），配的开关 `PET_UI_PERF_LOG` 也随模块一起没了。**不要把这些数字重新贴到当前固件头上。**

| 配置 | render_ms | fps | dirty_kb |
|---|---|---|---|
| 矩形版式（基线，30 秒 14 次采样） | 15 | 30 | 52 |
| 圆屏版式（环开，24 次采样） | 16–20（众数 17） | 28 | 28–29 |
| 圆屏版式（环关，A/B 对照） | 16–18 | 28 | 29 |

当时的结论：那 2 fps 不是新增图层造成的（把整个环图层跳过，帧率完全一致），差异来自猫画布 300²→320²；`dirty_kb` 从 52 降到 29 是因为面板不再每次重画横贯整屏的状态栏。同一份日志里记的内存是 `psram free 4527 KiB (min 4527)`、`internal free 71 KiB (min 37)`——**真正紧的是内部 SRAM**。

**仍未测**：当前固件的板端帧率、功耗/电流、温升。要拿到它们，用的是 §7 的那行 `app: PERF`，不是这一节的旧读数。

## 9. 诚实说明：哪些是实测，哪些是估算

| 数据 | 来源 |
|---|---|
| 猫的脏矩形尺寸、猫自己的范围、全量重绘范围 | **实测**，`build/host/cat3d_dirty_test.exe` @466×466，29 项检查 0 失败（本会话运行） |
| 各表面的尺寸与格式 | **读码**（`badge_ui.c`、`badge_cat.c`、`cat_view.c`、`sdkconfig.defaults`），字节数是按尺寸算的 |
| 猫的重绘像素数 / 耗时 | 宿主机上**未在本会话测量**；L7X @240 MHz 与桌面 CPU 差一个数量级，不能外推 |
| QSPI 带宽 20 MB/s | **估算**，按 4 线 × 40 MHz 保守取值，未在真机测过 |
