# 3D 渲染路线决策：自研 cat3d vs 原型 PCAT

这份文档回答一个问题：**固件的 3D 渲染走哪条路，只能选一条。**
它替换掉当前"两套渲染方案并存、谁也说服不了谁"的状态（`docs/gap-vs-v1.3.md:135` 记的就是这个状态）。

## 0. 结论

> **固件继续走自研 `components/cat3d/`。否决把 PCAT 作为固件渲染路线。**

否决 PCAT **不是**因为它不好，而是因为：**它唯一的实质优势（资产与贴图小 4 倍）落在 flash 上，而 flash 不是本项目的约束**；它另外的技术优势（16 位 z-buffer）要拿"一份从未在 ESP32 上跑过、也不存在 C 代码的全新移植"去换（参考实现 `ref.js` 本体 281 行，尚不含 C 侧容器解析与 LVGL 接线）。而**cat3d 这一侧的性能风险已经上板出清（15 ms/帧、30 fps，见 §6.2）**，PCAT 那侧的性能风险却只有在付完全部移植成本之后才能出清——风险不对称才是否决它的核心理由。**（原文此处写「本项目没有板子，这份移植无法在设备上验证」，该前提是错的：板子接着，见 §6。）**

⚠️ **本文的结论建立在"风险"上，原本不建立在"性能"上**（核查过程中，三条看似支持 cat3d 的性能论据——每帧带宽、host 计时、透视的代价——**全部被推翻或中和**，见 §2.2、§2.3、§5.2）。⚠️ **后记（2026-10-10）：§6.2 拿到了板端实测——cat3d 15 ms/帧、30 fps 稳定，即项目自己「互动态 ≥24fps」的验收线达成、余量 25%。所以本结论现在多了一条独立的性能支撑；但 §6.1 的翻案触发条件依然有效**（初始那三条性能论据被推翻这件事没有变，变的只是"cat3d 能不能跑得动"这个悬念被实测回答了）。唯一还站得住的 PCAT 技术优势（z-buffer）仍然指向 cat3d 的一个**未验证失效模式**（§5.2 第 5 条、§6 #4）。**若 cat3d 日后出现排序错误，本决定仍应被重新评估——§6.1 给了具体触发条件。**

现有 `components/cat3d/`、`tools/run-host-tests.cmd` 第一步、以及全部 golden 基准**原样保留**，不替换、不并存第二条渲染路径。

同时，本文纠正任务背景里的两条前提（见 §1 与 §2.1 末），并顺带记录两处工具缺陷（见 §7）。

**一句话摘要**：结论建立在**风险**上——核查中三条看似支持 cat3d 的性能论据（每帧带宽、host 计时、透视代价）**全部被推翻或中和**，剩下唯一站得住的 PCAT 技术优势（z-buffer）反而指向 cat3d 的一个未验证失效模式（§5.2 第 5 条、§6 #4）。**2026-10-10 补：板端实测 cat3d = 15 ms/帧、30 fps（§6.2），性能悬念出清且支持本结论。**

> ### ⚠️ 阅读提示（2026-10-12 补）：本文 §2 的数字是"决策当时"的数字
>
> 本文是一份**决策记录**，§2 的性能/带宽数字是在**旧固件围绕 300×300 猫画布**时测的，那时 `main/main.c` 里有一个 `CAT_VIEW_SIZE 300`。**那个常量已经不存在了**：当前固件的猫层渲染 466×466（desk/comp/aod），互动态渲染 233×233（`badge_cat.c` 的 `viewport_res()`，规范 `modes.play.res = 233`）。所以：
>
> - §2.1 的"帧缓冲 180,000 B"、§2.2 的"300×300 轨道"、§2.3 的 cat3d 三行带宽、§5.2 第 5 条的"180 KB 深度缓冲"、§6.1 的触发条件——**都按 300×300 时代的配置读**，不要当成当前固件的数字。当前固件的实测脏矩形与带宽账在 [`frame-budget.md`](frame-budget.md) §2–§3（466×466 视口）。
> - §6.2 的板端实测（15 ms / 30 fps / 52 KB）同样是**旧 UI 的观测点**，见 `frame-budget.md` §8 的说明。
> - **本文的结论不受影响**：它建立在风险与 PCAT 的移植代价上，与猫画布尺寸无关。
> - 当前的分层与重绘路线、已知偏差（含一条"原始理由算不过账"的更正）、宿主测试的覆盖边界，见本文 **§8 / §9 / §10**（本次新增）。

## 1. 必须先纠正的前提：golden 测试比对的是谁

任务背景把 golden 测试描述成"cat3d 的输出与 JS 原型逐像素比对"，并由此推出"若它比对的是 PCAT/`ref.js`，那么逐像素一致本身就说明两者可互换"。

**这个前提是错的。逐像素比对的对象不是 PCAT 的 `ref.js`，而是 `tools/firmware-ref.mjs` —— 一份对 cat3d 自身管线的独立重写。**

### 证据链（文件:行号）

| # | 事实 | 取证 |
|---|---|---|
| 1 | 一致性测试的入口 | `tools/run-host-tests.cmd:61` → `node tools\compare-render.mjs "build/host/frames" "components/cat3d/data"` |
| 2 | 比对脚本导入的参考实现是 `firmware-ref.mjs` | `tools/compare-render.mjs:14` → `import { buildTables, renderFirmware, BREED_NAMES } from './firmware-ref.mjs';` |
| 3 | 该文件自我声明为 **cat3d 同一管线的独立实现** | `tools/firmware-ref.mjs:1-13`：「This is an INDEPENDENT implementation of the same pipeline as components/cat3d … the same painter's algorithm, same auto-fit, same integer UV stepping」 |
| 4 | 它的几何来自 `.bbmodel`，不是 `.pcat` | `tools/compare-render.mjs:13,36` → `loadModel(CAT_MODEL_BBMODEL)`（`_ref/notion/pixel-cat.bbmodel`） |
| 5 | 它**没有**任何 PCAT 解析代码 | `tools/firmware-ref.mjs` 全文 451 行，无 `PCAT` / 块解析 / `TEX4` / `OUTF` 字样；其数据结构是 `tables.verts/parts/faces/keys/tracks/anims`（`firmware-ref.mjs:156`） |
| 6 | `ref.js` 根本不在测试路径上 | 对 `tools/`、`main/`、`components/`、`tests/` 全量搜 `ref\.js\|BadgeRenderer\|pixelcat\|badge-ref\|PCAT`，**代码侧 0 命中**；唯一命中全部在 `docs/gap-vs-v1.3.md` 的叙述文字里 |

### 算法层面也不可能是同一实现

`firmware-ref.mjs` 与 `cat3d.c` 同构，但与 `ref.js` 结构性不同：

| 维度 | cat3d.c / firmware-ref.mjs | PCAT `ref.js` |
|---|---|---|
| 矩阵 | 4×4 列主序（`cat3d.c:46-61` / `firmware-ref.mjs:30-42`） | 3×4 行主序（`ref.js:35-41`） |
| 投影 | **正交**，UV 在屏幕空间严格仿射（`cat3d.c:9-11`） | **透视**，逐像素透视校正 UV（`ref.js:151,239`） |
| 深度 | 画家算法 + 全画面平均深度排序（`cat3d.c:729,739-747`） | 16 位 z-buffer + 条带（`ref.js:109,234-246`） |
| 调度 | 全屏一次（`cat3d.c:688-747`） | 32 行条带分箱（`ref.js:205-258`） |
| 着色 | 32 级 Lambert LUT（`cat3d.c:152-154,188-196`） | 16 级 LUT（`ref.js:122-123`） |
| 贴图 | 原始 RGB565（`cat3d.c:490`） | 4bpp 索引 + 16 色调色板（`ref.js:242-244`） |

### 直接实测：两者输出确实不是同一张图

在同一台机器上把两路对同一标称姿态（yaw 0 / pitch 12 / idle t=0）各渲染一次 466×466：

```
cat3d case 01 : 唯一前景像素 39,480   渲染器自报写出像素 96,279（含重绘）  过绘 2.44×
ref.js  idle  : 唯一前景像素 36,752   ref.js 自报 st.written 49,265        过绘 1.34×
```

（命令见 §7；`cat3d` 的唯一前景像素是减掉背景渐变行色后数出来的，渐变按 `cat3d.c:215-226` 复算。）

**⚠️ 这不是受控 A/B**：两边的相机本来就不同——`cat3d` 用包围球自动适配的正交投影（`cat3d.c:253-254`），`ref.js` 用距离 62、看向 `[0,8.6,2.2]` 的透视相机（`ref.js:141`）。所以像素差里混了大量取景差异，这个数字只用来证明**两者不是同一张图**，不用来评价画质。

### 这条纠正对决策的影响

**golden 测试证明的是「cat3d 的 C 代码忠实地移植了 cat3d 自己的 JS 规范」，它对 PCAT 的兼容性一个字都没证明。** 所以"逐像素一致 ⇒ 两者可互换"这条推理不成立，决策不能建立在这个证据上。决策必须建立在别的证据上——即 §2 与 §4。

## 2. 两条路线的可量化对比

数据分三类，逐条标注：**实测**（本机跑出来的）、**推算**（有依据的估算）、**未验证**（还没测）。⚠️ 原写"无板不可知"，但板子是接着的（见 §6），所以"未验证"现在只表示**还没测**，不再表示**测不了**。

### 2.1 资产与内存

| 维度 | cat3d | PCAT | 标注 |
|---|---|---|---|
| 几何/动画表 | `cat_model.h` rodata **29,816 B** | 含在 `.pcat` 内 | 实测 |
| 贴图总量 | 6 × **131,072 B** = **786,432 B**（RGB565 256×256） | 6 × **32,768 B** = **196,608 B**（4bpp + 调色板） | 实测 |
| 资产总计（flash） | **816,248 B** | **205,624 B**（HEAD 14 / BONE 326 / CUBE 3,138 / OUTF 508 / ANIM 4,727 / TEX4 196,854） | 实测 |
| 框架状态 | `sizeof(cat3d_t)` host 64 位 = **20,152 B**；32 位推算 ≈ **20.1 KB** | `ref.js` 单实例除 `fb` 外 = **186,880 B**（`stripC` 29,824 + `stripZ` 29,824 + `tv` 86,400 + `tinfo` 23,040 + `tbox` 11,520 + `tclamp` 5,760 + `lut` 512） | 实测 |
| 帧缓冲 | 300×300×2 = **180,000 B**（PSRAM，**决策当时**；现固件 466×466×2 = **434,312 B**，见 `frame-budget.md` §1） | 无（条带式，见下） | 实测 |
| 可选 PSRAM 贴图缓存 | 131,072 B（`cat3d.c:633-647`，`CAT_TEX_BYTES`） | — | 实测 |
| **常驻 RAM 合计** | ≈ **200 KB**；开启 PSRAM 贴图缓存则 ≈ **331 KB** | ≈ **187 KB**（若按工具包文档的彩色条带双缓冲口径则 ≈ **217 KB**） | 推算（各项实测值求和） |

**取证说明**

- 贴图字节：`Get-ChildItem components\cat3d\data\*.bin` → 6 个文件各 131,072 B；`cat_model.h:6-8` 定义 `CAT_TEX_W/H=256`、`CAT_TEX_BYTES 131072`。
- 29,816 B：本机 `sizeof` 探针（§7），构成 = verts 5,376 + faces 14,784 + parts 1,792 + bones 224 + keys 7,360 + tracks 144 + anims 24 + names 112。
- 20,152 B：同一探针输出 `sizeof(cat3d_t)`。32 位换算只改 5 处指针/`size_t` 字段（`alloc`、`fb`、`tex_cache`、`tex_cache_len`、`last_bytes`），**属推算**。
- PCAT 段大小：工具包 `out/pixelcat.json:3-29` 原文，并用 `ref.js` 的 `parsePCAT` 独立解析复核得 `bytes=205624`、`TW=TH=256`、`bones=14`、`cubes=56`、可见面 **336**、`texs` 6 套各 32,768 nibble 字节。
- 186,880 B：直接读 `ref.js` 实例的 TypedArray `byteLength`（§7）。**注意**：`ref.js` 的 `fb`（434,312 B）是"模拟屏幕 GRAM"（`ref.js:107` 注释明写），真机面板自带 GRAM，不需要固件分配；cat3d 的 `fb` 则是 LVGL canvas 的真实需要。两者**不可直接相加比较**。

> **纠正任务背景里的一处口径**：背景把差异写成「内存占用（RGB565 纹理 768 KB vs PCAT 全量 205 KB）」。768 KB 是 **flash 里的贴图字节**，不是内存——`cat_assets_esp32.c:4-7` 明写这些贴图由 `EMBED_FILES` 链入镜像、**经 cache 直接读 flash，占 0 字节 SRAM**。真正的内存对比是上表最后一行：**两边大致相当（≈200 KB vs ≈187 KB）**，不是 3.8 倍之差。

**flash 是否是约束？——不是。** `partitions.csv:6` 给 `factory` 应用分区 **8 MB**，`sdkconfig.defaults:15` 是 32 MB NOR。cat3d 的 816 KB 约占应用分区的 **10%**。PCAT 省的 611 KB 换来的是别处的代价。

### 2.2 每帧 CPU 成本

> **⚠️ 本节数字不可复现，且已知原因是当时后台有并发负载。** 下表是初测（7 轮中位数），
> 测的时候同一台机器上有**固件构建在跑**。事后在空载机器上复测，**cat3d 与 `ref.js` 两侧
> 同向低约 1.5–2 倍**，且下表的 min/max 区间**不含**任何一次空载复测值。空载复测（6 轮
> 中位，`bench.exe` / `bench-ref.cjs`）：
>
> | 实现 | 本表 | 空载复测 |
> |---|---|---|
> | cat3d 300×300 脏矩形 | 0.300 ms | **0.197 ms**（0.153–0.213） |
> | cat3d 466×466 全画布 | 0.560 ms | **0.360 ms**（0.295–0.525） |
> | `ref.js` 466×466 全分辨率 | 3.233 ms | **1.907 ms**（1.724–2.200） |
> | `ref.js` 466 关透视校正 | 2.726 ms | **2.086 ms**（1.861–2.310） |
> | `ref.js` 233×233 半分辨率 | 1.553 ms | **0.748 ms**（0.736–0.984） |
>
> **比值方向不变**：初测 5.77×，空载 5.30×（独立复核另测得约 5.4–5.5×）。所以本节的**结论**
> （"不产出可用于决策的信号"）不受影响，但**绝对毫秒数只能当量级参考，不能引用**。
> 下面保留初测表以便与复测对照。

| 实现 | 分辨率 | 中位（有并发负载） | min / max |
|---|---|---|---|
| cat3d（C, GCC -O2） | 300×300 轨道（决策当时） | 0.300 ms | 0.177 / 0.453 |
| cat3d（C, GCC -O2） | 466×466 轨道 | 0.560 ms | 0.465 / 0.650 |
| PCAT `ref.js`（Node/V8） | 466×466 全分辨率 | 3.233 ms | 2.120 / 3.654 |
| PCAT `ref.js`（Node/V8） | 466×466，关透视校正（`opt.persp=false`） | 2.726 ms | 2.519 / 2.926 |
| PCAT `ref.js`（Node/V8） | 233×233 半分辨率 ×2 放大 | **1.553 ms** | 0.904 / 1.671 |

**比值：初测中位 5.77×（有并发负载），空载复测中位 5.30×。**

**⚠️ 三处不可比，必须同时声明：**

1. **语言不同**：cat3d 是 C（GCC -O2），`ref.js` 是 Node/V8 JIT。这是最大的一处混淆，且**无法在本机分离**。
2. **画布不同**：cat3d 跑 300×300（**决策当时**固件的配置；现在是 466×466，见文首提示），`ref.js` 跑 466×466（`SCR` 硬编码，`ref.js:11`）。**这一处对 cat3d 有利**，需归一后才公平。`ref.js` 自己给了参照：233 半分辨率（像素数为 466 的 1/4）中位 **1.553 ms**，即把像素量压到 1/4 只把耗时降到约 48%——说明 `ref.js` 有大量与像素数无关的固定开销（每帧 448 顶点 + 672 三角形分箱）。据此**粗估** `ref.js` 在 300×300 上约 **1.8–2.0 ms**，对 cat3d 的 0.300 ms 仍是约 **6–6.7×**。**这一步是推算，未验证；但它说明"画布不同"不足以解释掉整个 5.77×。**
3. **`ref.js` 另外画了一块地面柔光多边形**（`ref.js:126-128,210`），cat3d 没有。§2.3 已量化其字节成本；在 CPU 上它是额外的 16 边形扫描线填充，量级小但存在。

**⚠️ 这是 host 数字，不是板端数字，也不是受控 A/B。** 它混了 C 原生 vs V8 JIT 与两套算法的循环量，**不能直接读成"板端也快 5.77 倍"**（见 §6 #1/#1b）。

差异的结构性来源，以及一处**被实测证伪的直觉**：

- **两路的着色/写像素数在同一个量级，cat3d 反而更多。** 同为 466×466 轨道、同源模型，各自自报的遥测：

  | | cat3d | PCAT `ref.js` | 比值 |
  |---|---|---|---|
  | 边函数测试的像素中心 | 不统计（无此计数器） | 201,013 | — |
  | 进入重心插值/着色段的片段 | 不统计 | 84,483 | — |
  | 通过 z（或直接）真正写内存的像素 | **107,235**（`last_pixels`） | **55,468**（`st.written`） | **cat3d 1.93×** |

  cat3d 因为用画家算法（无深度测试），必须对着色像素全部写内存，过绘比约 **2.44 : 1.34**（§1 的单姿态实测）；PCAT 的 16 位 z 能挡掉约 1/3。所以**"cat3d 少画像素"是错的，它多写 1.93 倍**。
- 因此 5.77× **既不能归因于"cat3d 少画像素"（它多画），也不能归因于某个可分离的算法特性**——它落在"每着色像素的指令成本"上，而这部分正是被 C 原生 vs V8 JIT 混住的。**这就是它不可外推的原因。**
- ⚠️ **一处被证伪的直觉**：`ref.js` 有 `opt.persp` 开关，关掉即退化为仿射 UV（去掉逐像素倒数，`ref.js:239-240`）。**关掉并没有变快**，所以"透视除法是主要成本"不成立。
  - 初测时这一条我记岔了：正文写"2.627 → 2.726 ms，反而慢 3.8%"，而同节的表把 `persp=false` 记成 2.726 ms、比 `persp=true` 的 3.233 ms **更快**——两者方向相反，说明**这个差值在噪声内，初测根本分辨不出**。
  - 空载复测（各 5–6 轮中位）方向一致地为"关掉略慢"：`ref.js` 466 全分辨率 **1.907 ms** vs 关透视 **2.086 ms**（独立复核另测得 1.495 ms vs 1.608–2.015 ms，同方向）。慢约 9%，仍属噪声量级。
  - 结论不变且更强：**透视校正的开销在本机测不出来**，既不能当"PCAT 更贵"的理由，也不能当"正交更省"的理由。
- 另一处可确认的额外工作量：`ref.js` 按 32 行条带渲染，每个三角形在每条覆盖它的条带里都要重新做一次定点 setup（`ref.js:217-223`）。实测每帧 **360 个通过剔除的三角形**（`st.drawn`）产生 **568 次分箱**（`st.binned`），即**平均每个三角形被重复 setup 1.58 次**（`672 - 312 = 360`，见 `st.tris` / `st.culled`）。这是条带方案的确定性开销，与语言无关。

**结论：这一节不产出任何可用于决策的信号。** host 计时把"C vs JIT"和"算法差异"两件事混在一起，而我在本机无法分离它们（§6 #1b）；同时 cat3d 在**像素数上并不占优**（多写 1.93×）。所以这 5.77× 既**不能**读成"cat3d 更快"，也**不能**读成"PCAT 更快"。**两个方向都不成立，故本文不为任一方向引用它。**

`ref.js:272-273` 里还有一个作者自带的成本模型（`COST={vert:90,tri:350,bin:120,test:8,persp:40,affine:22,write:10,clear:2,mhz:240}`），并据此给出「466 全屏约 31–33 fps / 233 半分辨率约 90 fps」（工具包 `README.md:30-36`）。**该模型未经上板校准，属推算**，作者自己在 `README.md:27` 标注「粗估，上板实测后改」。注意其 `test:8` 与 `persp:40` 已经**涵盖**逐像素除法，且上表实测该除法在噪声内不可测——所以该模型对"透视很贵"的刻画偏保守，我不引用它的绝对毫秒数，只引用它"466 全屏接近极限"的定性结论。

#### ⚠️ 这一维度上 cat3d 实际上**不**占优——我撤回初稿的说法

初稿写的是"cat3d 领先约 2 倍"。这个比较有**两处不可比**，逐条修正后方向反转：

1. **`ref.js` 的脏矩形含一块地面柔光**（16 边形，`ref.js:126-128` 构造、`:210` 填充、`:192-193` 把它的顶点并进脏矩形范围），cat3d **没有**地面。把这部分去掉，轨道平均从 205,136 B 降到 **168,784 B**。
2. **两者的画布尺寸本来就不同**：cat3d 当时渲染 300×300 画布（`main/main.c:41` 的 `CAT_VIEW_SIZE 300`，**该常量现已删除**；当前固件的猫视口是 466×466 / 互动态 233×233），而 `ref.js` 的 `SCR` 硬编码 466（`ref.js:11`）。脏矩形面积按边长平方缩放，`(300/466)² ≈ 0.414`。

把 PCAT 归一到同样的 300×300 画布、并去掉地面：

```
168,784 B × 0.414 ≈ 69,900 B/帧   vs   cat3d 最坏 96,800 B/帧（典型 82,212）
```

**即：同画布、同"只画猫"的口径下，PCAT 的每帧送屏字节比 cat3d 更低（约 70 KB vs 82–97 KB）。**

我此前把这条算作"cat3d 的优势"是错的——差异全部来自**画布尺寸的选择**和**地面这一块 cat3d 没画的东西**，不是渲染路线的属性。**归零后，带宽对本决策没有指示作用。**（归一化本身是推算：假设脏矩形面积随画布面积等比缩放。）

一个仍然成立的、与语言无关的观察：在**各自**的配置下，cat3d 占 QSPI 带宽 14.5%（最坏），PCAT 占 30.8%（`ref.js` 自报口径，含地面），两者都在 20 MB/s 估算之内（该估算见 `frame-budget.md` §3、`ref.js:273` 的 `qspiMBs:20`，**估算本身是推算**）。**谁都不是瓶颈。**

**⚠️ 一个反直觉的实测结果**：PCAT 的 233 半分辨率模式**并不省 QSPI 字节**。因为它在送屏时做了 2×2 最近邻放大（`ref.js:257`：`st.bytes += (sy1-sy0)*2*(dx1-dx0)*2*2`，即每半分辨率像素送 4 个像素），而半分辨率脏矩形面积只有全分辨率的约 1/4，两者相乘正好抵平。实测两种模式送屏字节**完全相同**：

```
466 全分辨率  : tested 201,013  written 55,468  sent 205,136 B
233 半分辨率  : tested  53,882  written 13,871  sent 205,136 B   ← 送屏字节一模一样
```

所以工具包 `README.md:36` 建议的"互动档默认用半分辨率"**只降低 CPU，不降低带宽**。这一点在评估时容易被误读成"半分辨率同时省 CPU 和带宽"。

### 2.4 投影方式与观感

| | cat3d | PCAT |
|---|---|---|
| 投影 | 正交（`cat3d.c:9-11` 明确声明是刻意选择） | 透视，`F=(R/2)/tan(13.5°)`（`ref.js:151`） |
| 缩放 | 包围球自动适配 + `cam.scale` 可覆盖（`cat3d.c:253-254,665`） | `D` 距离参数（`ref.js:141`） |
| 观感差异 | 体素/像素美术的标准观感；平行线不收敛，转起来像"转盘" | 近大远小，更有"实体感" |

**观感差异属未验证**：有没有真机或高保真对比图，我无法判断 466×466 圆形 AMOLED 上哪个更好看，也不该在这里替美术下结论。可确认的是算法层面的差别：**正交让 u/v/z 在屏幕空间严格仿射，把除法全部留在三角形 setup 里**（`cat3d.c:9-11`）。⚠️ 但**不要**把它读成性能理由——§2.2 已实测证伪"透视除法是主要成本"。这里只说：正交的算法更简单（内层无除法），观感上更像体素玩具；透视更接近"实体"，代价是逐像素重心除法。**这是观感取舍，不是性能取舍。**

## 5. 最终结论、迁移代价与现有资产的处置

### 5.1 结论（单一）

**走自研 `components/cat3d/`。否决 PCAT 作为固件渲染路线。**

### 5.2 为什么否决 PCAT（具体理由，不是"各有优劣"）

1. **PCAT 的优势不在本项目的约束上。** 唯一实质领先的维度是 **flash 资产字节**（816 KB → 206 KB，见 §2.1；这是**镜像里占的 flash**，与 RAM 无关——贴图走 XIP，本来就不占 SRAM）。`factory` 分区是 8 MB（`partitions.csv:6`），816 KB 占 10%，所以省下的这 611 KB **换不来任何别的东西**：它既不缓解 RAM，也不接近分区上限。
2. **要付的代价是全部，不是增量。** PCAT 没有 C 代码。`ref.js` 是 281 行 JS（`ref.js:1-281`），含定点 28.4 边函数、16 位 z、透视校正、条带分箱、调色板采样；把它变成固件需要一份全新的 C 渲染器 + `PCAT` 容器解析 + LVGL 接线 + 一整套新的基准测试。**没有一处可以复用 cat3d 已验证的代码。**
3. **这份移植的验证会循环，而且现在连"没板子"这个借口也没了**（原文写"没有板子，这份移植无法验证"，措辞已更正——板子其实是接着的）。真正的问题不是没有设备，而是：把 `ref.js` 移植成 C，再拿 `ref.js` 做基准，只能证明"移植忠实"，**不能证明"这个算法在 ESP32-S3 上跑得动"**——后者要在板子上测，而那时你已经把整份渲染器写完了。而 cat3d 恰好已经越过了这道坎：**上板实测 15 ms/帧、30 fps**（§6.2）。所以风险不对称：cat3d 的性能风险已经出清，PCAT 的性能风险只有在付完全部移植成本**之后**才能出清。
4. **透视在本设备上是负分。** 466×466 圆形 AMOLED 上的像素风电子宠物，正交是体素美术的常规观感；正交还让 UV 在屏幕空间严格仿射，内层循环只剩定点加法与查表（`cat3d.c:483-498`），算法上更简单。**但注意**：实测 §2.2 已证伪"透视除法是主要成本"——关掉透视校正反而慢 3.8%（噪声内）。所以这一条只作为**观感与算法简洁性**的理由，**不作为性能理由**。
5. **一处 PCAT 的"优势"经核查后**不缩水，反而更重要****——z-buffer vs 画家算法。既然 §2.2/§2.3 的性能论据全被中和，**"z-buffer 更稳健"就成了 PCAT 唯一还站着的技术优势**，而它恰好指向一个真实的失效模式：新增 32 个服饰方块后，画家算法的**平均深度排序**可能给出可见的前后关系错误（§6 #4 已列为未验证项，且 golden 测试**测不出来**）。
   - **诚实的代价对比**：cat3d 当前 336 面全是互不相交的凸方块，画家算法在这个具体模型上**未被观测到错误**（10 个姿态、2,171,560 像素全过）。但"未被观测到"不等于"不存在"，而加服饰会引入新的排序场景。
   - **如果真的出现排序错误**，最小修法是给 cat3d 加一个真正的深度缓冲（放在**决策当时的** 300×300 画布上是 180 KB，PSRAM 够用；按当前 466×466 视口则是 **434,312 B**——`frame-budget.md` §1 记了三张 466×466 表面都在 PSRAM 里，余量仍在）——**这比引进 PCAT 全栈小得多**，也是 §6.1 的触发条件之一。
   - **16 级 vs 32 级光照**：这是能力差异不假，但 32 级是**更多**的档位，cat3d 不因此吃亏。
6. **成长缩放 cat3d 现成、PCAT 没有**（§4.3）。

#### 我明确撤回的两条"理由"

这两条看起来很支持"保留 cat3d"，但核查后**站不住，甚至反向**。列在这里，以免被后人重新捡起来当作论据：

- ❌ **"cat3d 每帧送屏字节只有 PCAT 的一半"**：**方向是错的。** 加上两处修正（`ref.js` 的脏矩形含一块 cat3d 没有的地面多边形；两者的画布尺寸本来不同 300 vs 466）后，同口径下 **PCAT 更低（约 70 KB vs 82–97 KB）**。详见 §2.3。
- ❌ **"cat3d 的每帧计算便宜 5.77×"**：那是 C 原生 vs V8 JIT 的对比，两者不可分；而且 cat3d 因无深度测试**多写 1.93 倍像素**（§2.2）。**这条在任何意义上都不能作为板端论据。**

#### 那么真正支撑结论的是什么

只有三条经得起核查，**全部与性能无关**：

1. **flash 不是约束**（816 KB / 8 MB 分区 = 10%），所以 PCAT 唯一**确定**的实质优势（贴图小 4 倍、资产小 4 倍）不落在本项目的约束上；
2. **cat3d 已验证且已接线**（2,171,560 像素 golden + LVGL 脏矩形 / 自适应帧率 / 遥测全部就位）；
3. **PCAT 无 C 代码，且其 host 验证会循环**（拿 `ref.js` 验 `ref.js` 的 C 移植）；它的板端性能只有在移植完成后才能测，而 cat3d 的板端性能**已实测达标**（§6.2）。~~移植在无板条件下无法验证~~ —— 措辞已更正，板子接着。

### 6.2 板端实测（2026-10-10）：cat3d 侧的数字已经拿到

原文把 #1 列为"无板不可知"，而这是本决策唯一的性能悬念。它现在有了答案，**且答案支持原结论**：

```
FPSPROBE render_ms=15 fps=30 dirty_kb=52      ← 串口连续采 30 秒，14 次采样一字不差
```

| 项 | 实测 | 对本决策的意义 |
|---|---|---|
| 单帧光栅化 | **15 ms** | 占 30 fps 帧预算（33.3 ms）的 **45%**，未触及 `cat_view` 自适应降速阈值（3/5） |
| 帧率 | **30 fps**（目标值达成，非被截断） | §9.3 的「互动态 ≥24fps」验收线**达成，余量 25%** |
| 脏矩形 | **52 KB** | 全屏 434 KB 的 **1/8**，§3 带宽账成立 |

**这改变了什么**：原文说"结论不建立在任何性能预测上"，那是防守性措辞；现在可以更进一步——**cat3d 在真机上确实满足了项目自己的帧率验收线，且余量健康**。所以 §5「继续 cat3d」这个结论现在同时站在**风险**（原三条理由不变）与**实测性能**（新增）两条腿上。这是把结论**加强**了，不是推翻它。

（方法与口径见 `docs/frame-budget.md` §8；探针是临时的，测完已删除、板子已刷回不含探针的版本。**这是矩形版式下的基线**：圆屏版式与圆裁 `clip_corner` 会引入一个中间图层，落地后必须重测。）

**仍然未知、且只有真机移植才能回答的**：PCAT 侧的同等数字。#1b 那个"未闭合的证据缺口"**没有**因为这块板子而闭合——因为 PCAT 没有 C 代码，"在设备上验证它"这件事本身就是那个待评估的移植工作量。换句话说：**板子的存在让 cat3d 的结论变强了，但没有让 PCAT 变得更接近可用。**

### 6.1 什么条件下应该重新考虑这个决定

本文的结论**不是**"PCAT 永远不该用"。它依赖的板端假设一旦被真机数据推翻，就该翻案。具体的触发条件（✅ = 已触发过检查）：

| 拿到板子后，如果出现 | 那么 |
|---|---|
| ✅ **已检查，未触发** —— cat3d 在 300×300（**决策当时的视口**；现为 466×466） / 30 fps 下**无法**在 3/5 占空比内完成一帧（即 `render_us_avg` > 20 ms 且自适应已降到 12 fps 仍不达标）。闸门的定义在 `main/ui/cat_view.c`：`CAT_VIEW_DUTY_NUM/DEN = 3/5`、`CAT_VIEW_MIN_FPS 12` | 重新评估。此时"已验证"这条优势被性能打掉，PCAT 的 z-buffer/半分辨率方案值得重新做一次真实 C 移植对比。**旧配置实测：15 ms < 20 ms，帧率 30 fps 未被降速**（§6.2）→ **本触发条件不成立**（按当前 466×466 视口**未重测**） |
| 服饰方块加进画家算法后出现**可见的排序错误**（方块穿插、前后关系错误） | 这正是 #4 说的 golden 测试**测不出来**的失效模式。此时"z-buffer"从"可放弃的优势"变成"必须解决的缺陷" |
| flash 因玩法层（毕业/繁育/委托/手记，见 `docs/gap-vs-v1.3.md:16`）膨胀到接近 8 MB 分区上限 | 重新评估 4bpp 贴图压缩（816 KB → 206 KB）。**注意**：这只需要给 cat3d 换贴图格式，**不需要换渲染器** |
| 美术明确要求透视观感 | 那是观感需求变更，不是工程决策；正交转透视要改投影与 UV 插值，属一次局部改造，仍不必引进 PCAT 全栈 |

反过来，**下面这些不构成翻案理由**（都已在 §2 与 §5 里被单独核查并否决过）：

- "host 上 `ref.js` 比 cat3d 慢 5.77 倍" → 语言混淆，方向不可用（§2.2）；
- "cat3d 省一半屏带宽" → 反过来，同口径下 PCAT 更低（§2.3）；
- "PCAT 的贴图小 4 倍" → flash 不是约束（§2.1）；
- "PCAT 有现成的 `setOutfit()`" → 那份"现成"建立在一份尚不存在的 C 渲染器上（§4.1）；
- "透视除法很贵" → 实测在噪声内不可测（§2.2）。

## 8. 当前固件的渲染路径（2026-10-12 补）

§1–§7 是"选 cat3d 还是 PCAT"的决策记录。这一节写**决策落地后，现在这套固件实际长什么样**，只写分层与重绘路线；性能预算在 [`frame-budget.md`](frame-budget.md)，构建与运行在 [`build-and-usage.md`](build-and-usage.md)，**不在这里重复**。

### 8.1 图层顺序（0 在底）

| 索引 | 层 | 内容 |
|---|---|---|
| 0 | 猫画布 | cat3d 渲染的 RGB565 canvas，只失效自己的脏矩形 |
| 1 | face 画布 | ARGB8888 全屏：圆盘、状态弧、环、图标、按钮等参考里用 canvas 画的全部图元 |
| 2 | 文本控件 | 只有文字用 LVGL widget（要它的字形与字距） |
| 3 | 合成层 | 气泡 / toast / 边环闪光 / 浮动数字（`comp` 画布） |
| 4 | 过渡快照 | 切屏滑动用的整屏快照（`trans` 画布，首次切屏时创建） |

顺序用 `lv_obj_move_to_index()` 显式设定，**不靠创建顺序**。`badge_ui.h` 顶部写明这是一处 bug 修复：上一版文档写的是 "bezel under cat"（表壳在猫下面），代码却先创建猫，于是**文档里的栈序和真实的栈序相反**，而当时没有任何测试能看见它。

### 8.2 重绘路线

- **切屏**：重建控件 + 整块 face 重绘（`badge_ui_rebuild()`）。
- **每 tick**：`badge_ui_refresh()` 只重绘**变化过的盒子**——盒子列表由 `badge_ui_plan.c` 给出（上限 32），`badge_ui.c` 清这些盒子并且只重画与它们相交的元素。一个属性弧动 1 点 = 一条带，不是 1.7 MB。
- **猫**：只失效 `cat3d_dirty_rect()` 返回的矩形（上一帧 ∪ 当前帧，见 `frame-budget.md` §2）。
- **文字**：控件文本变了才更新；`ui_resolve_vars()` 通过 `badge_ui_expand()` 实现规范的 `fill()` 语法（`{careLabel:<key>}` 先替换，其余 token 再替换两轮）。
- **过渡**：`UI_TRANSITION_MS 220`，`e = 1 - (1-p)^3`，快照在**重画 face 之前**从 face 缓冲取。

### 8.3 过渡方向的约定

参考的合成方向是 `up:[0,-1] down:[0,1] left:[-1,0] right:[1,0]`，缓动 `1-(1-p)^3`；`badge_numbers.transition_ms` 非 0 时覆盖 `UI_TRANSITION_MS`。这两条都在 `badge_ui.c` 里，与规范一致，**不属于偏差**。

## 9. 已知偏差（规范/参考 vs 固件，逐条列清）

这一节列出**当前固件与规范/参考渲染器有意不一致**的地方。凡是固件自己选的值，都注明"这是固件选择，不是规范值"。**§9.2 是一条更正**：原始说法在代码里，但按两边的代码实算对不上账，所以它不算偏差；写在这里是因为它在 `main/` 的注释里、会被下一个人当成既成事实引用。

### 9.1 `{brightText}`：固件显示百分比，参考显示 低/中/高

| | 值 | 出处 |
|---|---|---|
| 规范 | **没有定义 `{brightText}` 的措辞**——元素 `val_bright`（`font: f20`, `align: right`, `{brightText}`，`badge_spec.json`）只有模板，`texts` 里没有对应字符串 | `_ref/baji-spec/吧唧交互规范/badge_spec.json`（`val_bright` 元素） |
| 参考渲染器 | 从字面量表填：`const BRIGHT=[['低',.45],['中',.75],['高',1]]`（第 1325 行），`fill()` 里 `brightText:BRIGHT[ST.set.bright][0]`（第 1339 行）——显示**档位名** | `_ref/baji-spec/吧唧交互规范/吧唧渲染参考.html:1325,1339` |
| 固件 | `ui_bright_text()` 用 `snprintf(out, cap, "%u%%", badge_bright_scale_pct[level])`，三档是 **45 / 75 / 100**，即屏幕上显示 `45% / 75% / 100%` | `main/ui/badge_ui.c` 的 `ui_bright_text()`；`badge_bright_scale_pct[BADGE_BRIGHT_LEVELS] = { 45, 75, 100 }` 在 `main/ui/badge_fsm.c`（`BADGE_BRIGHT_LEVELS 3` 在 `main/ui/badge_fsm.h`） |

**这是固件选择，不是规范值。** 三个百分比**就是**参考表里 `BRIGHT[..][1]` 的三个缩放值换成整数，所以数字本身不是新编的；但"在界面上显示数字而不是档位名"这一步没有规范依据。

**原因（`badge_ui.c` 里写的是字形覆盖，但这条理由经核查不成立）**：`badge_ui.c` 的注释说这三个字里"只有 中 在 f20 里，另两个会变成空方块"。本会话直接解析了四个字体文件的 cmap 与字形注释，**结论是相反**：

| 字 | U+ | f16 | f20 | f24 | n40 |
|---|---|---|---|---|---|
| 低 | U+4F4E | 有 | **有** | 有 | 无 |
| 中 | U+4E2D | 有 | **有** | 有 | 无 |
| 高 | U+9AD8 | **无** | **有** | **无** | 无 |

（方法：按 LVGL 的 `get_glyph_dsc_id()` 约定解析每个文件的 `cmaps[]` 与 `unicode_list_*`，再与该文件自己的 `/* U+XXXX "字" */` 字形注释交叉核对——`badge_f20.c` 里 `U+4F4E`、`U+4E2D`、`U+9AD8` 三条注释各自对应一个真实的字形描述符条目。`低` 与 `中` 在 f16/f24 里也有；`高` 只在 f20 里有，而亮度值这个元素（`val_bright`）本来就用 f20。）

所以"字形不够"这个理由**只对 f16/f24 成立，对实际绘制它的 f20 不成立**（`check-font-coverage.mjs` 的 24 个 informational 缺字里也**没有**这三个字）。**真正成立的说法是**：`{brightText}` 的措辞在规范里**根本不存在**，参考用的是 `BRIGHT[i][0]`（档位名），固件选了 `BRIGHT[i][1]`（缩放值）并把它格式化成百分比；这是**固件的选择**，参考、规范都没有这么说。**已把这件事回报给 Lead**（`badge_ui.c` 的注释需要更正，但那在 `main/` 里，不在本文件的写范围内）。

### 9.2 toast 的宽度在绘制时被夹紧——但这条"偏差"的原始理由算不过账

**先写结论**：`badge_ui.c` 确实对 toast 宽度做了一次安全圆夹紧，代码在、逻辑清楚；**但按两边自己的代码读，这个夹紧对规范的数值不起作用**，而且它引用的"四角超出 4 px"与固件/参考自己的摆放方式对不上。所以这里**不是**一条"规范违反了自己的安全圆、固件修正它"的偏差，而是一条**代码里的防护 + 一处自相矛盾的注释**。原始来源的说法如下，再附我按代码算出来的结果。

源头的说法（两处，用词一致）：

- `main/ui/badge_geom.h:96-105`（`badge_safe_half_width_at()` 的文档）：*"the toast is specified at y=380, h=40 with maxW=220, and 220 wide at that height puts its corners 216 px from the centre -- four pixels outside the safe radius of 212."*
- `main/ui/badge_ui.c:62-75` 重复了同一句，并说 `badge_geom.h` 拥有那套算术、**规范没有被改**（"220 is its intended width"）。
- 实现：`badge_geom.c:274-279` —— `dy = |y_bottom - 233|`，`dy >= 212` 返回 0，否则返回 `sqrt(212² - dy²)`。
- 用它的地方：`badge_ui.c:990-993` —— 先 `w = min(文字宽 + 2×18, 220)`，再 `half_max = badge_safe_half_width_at(BADGE_TOAST_Y + BADGE_TOAST_H / 2)`，若 `w/2 > half_max` 则 `w = half_max * 2`。

按这些代码里的数字实算一遍（本会话算过，不是估计）：

| 问题 | 结果 |
|---|---|
| toast 的矩形在哪 | `badge_ui.c:997` 用 `y0 = BADGE_TOAST_Y - BADGE_TOAST_H/2 = 360`、`h = 40` → **360..400**，即 **`y=380` 是中心线**，不是上边 |
| 参考渲染器怎么摆 | `吧唧渲染参考.html:1531` 的 `drawToast()`：`rrect(C-w/2, K.y-K.h/2, w, K.h, K.radius)` —— **同样把 `K.y` 当中心线** |
| 220 宽、底边 400 的四角距圆心 | **200.0 px**（√(110² + 167²)），**在半径 212 以内** |
| 那 216 从哪来 | 只有把 `y=380` 当**上边**（矩形 380..420）才算得出 ≈217 px。也就是说这条注释用的是"y 是上边"的摆法，而**固件和参考都把 y 当中心线** |
| 夹紧对规范数值是否生效 | `badge_safe_half_width_at(400)` = **130** → `w = 260`；但 260 已经先被 `BADGE_TOAST_MAX_W 220` 夹掉了，判定是 `110 > 130` **不成立** → **夹紧不生效**。它只在盒子更靠近边缘时才会咬（例如底边到 415 时 `2×half_max = 216 < 220`） |

**所以要怎么写才诚实**：这是一层**比规范更严的防护**，留着是对的（toast 文字一变长、或位置一调，它立刻有用），但**不能再说"规范的 220 px 违反了它自己的安全圆"**——那是把 `BADGE_TOAST_Y` 读成上边才成立的算术，与 `badge_ui.c` 自己的 `y0 = Y - H/2` 和参考的 `drawToast()` 都矛盾。规范没有被改也不需要改。**已回报 Lead**：`badge_geom.h` 与 `badge_ui.c` 的那两段注释应当改掉（都在 `main/` 里，不在本文件的写范围内）。

（附一条同源的边界：即便按"y 是上边"的读法，`badge_safe_half_width_at(420)` = 99 → `w = 198`，夹紧会把 220 收到 198，即"窄 22 px"而不是"窄 4 px"。所以原文里"比规范窄约 4 px"这个代价估计在任何一种读法下都不成立。）

### 9.3 猫：三处有意的替换，与 cat3d 没有的轨道

`main/ui/badge_cat.c` 顶部写着 "THREE DELIBERATE DIFFERENCES FROM THE PROTOTYPE"，逐条：

| 参考的指令 | 参考里的含义 | 固件怎么做 | 为什么 |
|---|---|---|---|
| `dim` | 参考逐像素缩 r/g/b | 用 canvas 的 `lv_obj_set_style_opa()` 做同一个乘法的合成器版本；AOD 强制 0.35 | 同样的算术，交给合成器，省一次逐像素循环 |
| `look_x` / `look_y` | 参考旋转**头部骨骼** | **cat3d 没有头部轨道**，所以把这组值用到身体的转台（yaw/pitch）上 | 数据有了，挂点没有：不接就等于丢行为 |
| `follow_finger` | 参考让猫看向手指 | 身体小幅转台 | 同上 |
| 追尾巴 / 被自己吓到 | 参考是 720° 自旋 / 跳跃 | 自旋：`root_yaw` 的 720°；跳跃：`root_y` 的竖直平移到 `|sin|*4` 模型单位 | 模型有 `root_yaw` / `root_y`，但没有头部与"跳"的轨道 |

**要点**：这不是"少做了"，而是**把参考的语义挪到 cat3d 真正拥有的控制量上**。代价是"转头看手指"这个动作在观感上变成了"整个身体转"，而且**被自己吓到的跳跃是一个整模型竖直平移，不是重心起伏**。

另外两条与渲染路径相关的既定事实：

- **互动态走 233×233 半分辨率**（规范 `modes.play.res = 233`），`badge_cat.c` 的 `BADGE_CAT_HALF_RES 233`，首次进入才创建、之后保留。**这块半分辨率画布没有做 2× 放大上屏**：`present()` 只把 `lv_obj_center()` 居中，固件里没有任何 `lv_obj_set_style_transform_scale` / zoom 调用。参考渲染器在 `modes.play.doc` 里写的是"半分辨率 233 渲染后 2× 放大"；按当前代码，那一步**没有实现**（`cat_view.c` 的 canvas 就用 `w×h` 铺在中心，周围是其它图层）。
- **猫的画布是整块 466×466，不是"只取猫的范围"**：`badge_cat.c` 用 `cat_view_create(parent, BADGE_SCR_W, BADGE_SCR_H)`，屏幕的 `cat.dist/ox/oy` 被映射成相机参数（`badge_cat.c` 顶部的投影公式）。`main/ui/cat_view.h` 顶部"画布只取猫的屏幕范围"那句注释与现在的调用点不一致，照代码读。

### 9.4 App 链路与"地点"：规范有三个地点，固件是编译期常量

- 规范的 `places` 有三个：工作 / 咖啡店 / 公园（`badge_spec.json` 的 `places`；`BADGE_PLACE_COUNT 3`）。
- 生活同步屏要显示"当前在哪"，但**这个值不在任何一帧里**：`badge_spec.h` 的 `badge_evt_type_t` 没有"地点"事件，`net_link` / `net_proto` / `net_social` 也没有这个字段（唯一的 place 索引是 `EVT_CALL_HOME.a`，那是**离开**徽章的命令）。
- 所以 `main/main.c` 用 `#define APP_PLACE 0`，并在 `badge_ui_set_place(s_ui, APP_PLACE)` 里显式设进去；`_Static_assert(APP_PLACE >= 0 && APP_PLACE < BADGE_PLACE_COUNT)` 把越界问题放在编译期。
- **这是缺口，不是偏差**：`badge_ui_set_place()` 默认值是 0，也就是规范的第一个地点（参考里 `let place='work'` 的默认值）。等 App 真的下发地点（二期），改的是这一个常量/一处调用。

### 10.1 `ui/badge_ui.c` 没有宿主测试，以及为什么

`badge_ui.c` 是全仓**唯一**真正调用 `lv_canvas_*` / `lv_label_*` / `lv_obj_*` 的文件。给它写宿主测试，等于断言一个**手写的 LVGL 垫片**：测试通过只能说明"垫片按我以为的方式工作"，不能说明 LVGL 在真机上会那样做。所以覆盖它的是别的东西：

1. **它能被固件的编译器编过**：`main/CMakeLists.txt` 对 `main` 组件自己的源码开 `-Wall -Wextra -Werror`，而 `tools/run-host-tests.cmd` 里各阶段用 `xtensa-esp-elf-gcc -Werror=all` 再编一遍**同一批头文件**。这套编译纪律在这个仓里不是形式主义：它曾经抓到过"clang 干净、GCC 14.2 报错"的差别（`run-host-tests.cmd` 里记着那次事故）。
2. **它按设计足够薄**：盒子列表来自 `badge_ui_plan.c`（宿主测试覆盖），标签几何来自 `badge_geom.c`（宿主测试覆盖），像素来自 `badge_paint.c`（宿主测试覆盖真实像素）。`badge_ui.c` 剩下的是"把这三样喂给 LVGL"。
3. **`badge_ui_dump_ppm()` 是为将来准备的**：它可以把整屏导出成 PPM 以便宿主机整屏比对。**本会话没有看到任何调用它的测试**——它现在是一个可用的钩子，不是已有的证据。

**两个只有靠读代码才能发现的 z 序缺陷已修，并把原因写在代码里**：

- **LVGL 9 按子对象索引升序绘制，索引 0 在最底**（`managed_components/lvgl__lvgl/src/core/lv_refr.c` 的绘制循环）。上一版文档写"表壳在猫下面"、代码却让猫先创建，于是文档与真实栈序相反。
- **`lv_obj_clean()` 会连气泡/toast/浮动数字的 label 一起删掉**：它们虽然不在"文本层"这个容器里，但都在同一棵子树下。现在改成**逐个删除这一屏自己建的 label**，不移除整个子树。

这两条都是**读代码发现的，不是测试发现的**——也正是 §10.1 存在的理由：这一层没有自动化覆盖，只能靠"薄 + 可编译 + 写清原因"来兜底。
