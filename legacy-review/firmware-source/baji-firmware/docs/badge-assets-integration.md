This file is the record of how the specification's icons, prompt sounds and fonts
reach the glass: which files are generated, which are vendored, how they get
`lvgl.h`, what the host phase proves, and what it deliberately does not.

**Status at this pass (2026-10-12): the wiring is done and green.** `main/CMakeLists.txt`
registers all of it (§1), the icon-count disagreement is resolved by registering
`bolt` in the generator (§2a), and the font coverage check passes with 24
informational (non-fatal) misses that are all prose (§3).

### 1a. The font files need `-DLV_LVGL_H_INCLUDE_SIMPLE`

`main/ui/fonts/badge_f*.c` were generated by `lv_font_conv` and start with

```c
#ifdef LV_LVGL_H_INCLUDE_SIMPLE
#include "lvgl.h"
#else
#include "lvgl/lvgl.h"
#endif
```

`"lvgl/lvgl.h"` does not resolve in this project: LVGL 9.5.0 is installed as
`managed_components/lvgl__lvgl/` (there is no `managed_components/lvgl/`), so
`-I managed_components/lvgl__lvgl -I managed_components` leaves `lvgl/lvgl.h`
unfindable, and `../` relative to the file is `main/ui/`, which has no `lvgl.h`
either. `main/` does not define the macro and ESP-IDF's LVGL component only sets
`LV_CONF_INCLUDE_SIMPLE`.

Verified: compiling the vendored files with one of this project's real
`compile_commands.json` argument lists (from `D:\orangecat-build`, IDF v5.5.5)
fails with `fatal error: lvgl/lvgl.h: No such file or directory` for all four, and
succeeds cleanly with `-DLV_LVGL_H_INCLUDE_SIMPLE` added.

So the component needed this line, and it is now in `main/CMakeLists.txt`:

```cmake
target_compile_definitions(${COMPONENT_LIB} PRIVATE LV_LVGL_H_INCLUDE_SIMPLE)
target_compile_options(${COMPONENT_LIB} PRIVATE -Wall -Wextra -Werror)
```

Both are registered today, and the `-Werror` is scoped to the `main` component's
own sources, so the vendored faces cannot fail the build through a warning a
vendor file carries. The host phases are unaffected because they never compile the
font files (see 4).

## 2. Regenerating and checking

```powershell
node tools/gen-badge-assets.mjs            # write main/ui/badge_assets{,_data}.c
node tools/gen-badge-assets.mjs --check    # write nothing; exit 1 when stale
node tools/check-font-coverage.mjs         # exit 1 on any character with no glyph
tools\suite\05-assets.cmd                  # all of the above plus the host test
```

The generator is dependency-free (Node's built-in `zlib` decodes the PNGs) and
deterministic: two consecutive runs produce byte-identical output (checked). It
refuses to guess rather than emit something plausible:

* an icon `badge_icon_names[]` names but the package has no PNG for -> error;
* a PNG that is not `BADGE_ICON_PX` x `BADGE_ICON_PX` -> error;
* an icon that is fully transparent -> error;
* a sound that is not 16 kHz / 16-bit / mono, or that disagrees with the
  package's own `sounds/badge_sounds.c` sample for sample -> error;
* a total mismatch between the icon set and the package -> error.

### 2a. `bolt.png`: RESOLVED -- the generator registers it as a 28th index

The package ships **28** icons. `badge_spec.json` references 13 icon names and
names no element that draws `bolt`, while `main/ui/badge_assets.h` (frozen) says
"28 icons". That disagreement was resolved on the **generator** side, not by
editing the spec: `tools/gen-badge-ui.mjs` appends `iconOf('bolt')` after the
element walk, with the reason written in place:

> One icon is registered here, after that loop, because no element names it:
> `bolt`. The package's own `badge_ui_spec.h` declares `BADGE_ICON_BOLT`,
> `icons/bolt.png` ships, and the reference renders it in the battery element
> (`if(ST.usb) icon('bolt', ...)`) -- but `badge_spec.json` has no element for it.
> Appending it makes `BADGE_ICON_COUNT` 28, the count `badge_spec.h` documents and
> the count the package ships; it lets `badge_paint_battery()` draw the real bolt,
> and makes the assets generator's "the emitted set is exactly `icons/*.png`"
> assertion complete. Appending rather than prepending matters: the dynamic-icon
> sentinels and every other index stay where they were.

Verified this pass:

```
$ node tools/gen-badge-ui.mjs --check
gen-badge-ui: up to date (23 screens, 151 elements, 24 colours, 402 strings)
$ node tools/gen-badge-assets.mjs --check
gen-badge-assets: up to date (28 icons (28672 B of RGBA), 5 sounds (22480 samples))
```

`main/ui/badge_spec_data.h` now has `BADGE_ICON_COUNT 28` with
`BADGE_ICON_BOLT 13`, and `badge_assets_data.c` declares its icon table
`[BADGE_ICON_COUNT]` with `badge_icon_bolt_data[16*16*4]` present. So the assets
generator's unreferenced-icon warning is gone and `assets --check` exits 0.

### 3a. `{brightText}` and the `低/中/高` glyphs -- the code comment is wrong

`main/ui/badge_ui.c` chose to render the settings screen's `{brightText}` as the
level's percentage, and the comment there justifies it by claiming "two of those
three glyphs are not in the shipped f20 face -- only 中 is". That claim does not
hold, measured directly from the font files this pass (each face's own
`/* U+XXXX "字" */` glyph descriptors):

| character | badge_f16 | badge_f20 | badge_f24 | badge_n40 |
|---|---|---|---|---|
| 低 U+4F4E | yes | **yes** | yes | no |
| 中 U+4E2D | yes | **yes** | yes | no |
| 高 U+9AD8 | **no** | **yes** | **no** | no |

`val_bright` is an `f20` element, and `badge_f20.c` carries all three. (高 is the
one that is missing from the 360-symbol `"ui"` faces f16/f24 -- which is probably
where the mistake came from.) The percentage rendering is still a legitimate
**firmware choice** -- the spec defines no wording for `{brightText}` at all -- but
it is not forced by a glyph gap. Recorded in
[`render-route.md`](render-route.md) §9.1 and reported to the Lead;
`main/ui/badge_ui.c` is not this pass's to edit.

### 3b. Where the remaining informational misses come from (GB2312 analysis)

This analysis is why the 24 remaining misses are inert rather than fixable-by-one-command.

* U+3002 。, U+FF1B ；, U+FF08 （, U+FF09 ）, U+2014 — **are in
  `fonts/NotoSansSC-Medium-subset.otf`** and were simply left out of the
  `--symbols` argument that produced the four `.c` files. Adding them to the
  symbol list and re-running `lv_font_conv` would fix those five in one pass -- and
  would also add glyphs nothing on the glass needs, since every one of them sits in
  prose or in a field the badge never renders.
* U+00B0 °, U+00B2 ², U+03A9 Ω, U+2013 –, U+2260 ≠, U+6E32 渲, U+54AA 咪,
  U+6123 愣, U+66B9 暹, U+8393 莓 are **not in the subset OTF either** (checked by
  parsing the OTF's own cmap and by re-encoding through GB2312):

  * 咪 愣 暹 莓 渲 are GB2312 **level 2** (GB2312 byte 0xDF 0xE4 ... 0xE4 0xD6).
    The licence note says `badge_f20` carries "GB2312 一级常用 3755 字" -- level
    *one* -- so level-2 characters being absent is consistent with the note, and
    the firmware's own strings (咪, 愣, 暹, 莓) are what fall outside it.
  * 。 ； （ ） ° Ω ≠ are GB2312 *symbol* rows (0xA1/0xA3/0xA6 lead bytes), not the
    3755 hanzi, so a level-1 hanzi list would not have covered them either.
  * — (U+2014) and – (U+2013) and ² (U+00B2) are not in GB2312 at all; — happens
    to be in the subset OTF and the other two are not.

Consequences for the shipped strings (the parts that are still live work):

1. the four firmware literals that are not in the subset (咪, 愣, 暹, 莓) are
   **breed and item names in `main/net/net_proto.c` / `main/pet/pet_state.c`**, and
   `check-font-coverage.mjs` classifies them as "not on the glass": they reach the
   radio and the App, not a label. So they are not a reason to regenerate anything.
   Renaming them would be a product decision, not a font fix.
2. if a prose string ever *becomes* a drawn string, that is the moment to add its
   characters -- and the coverage check is what will say so.
3. whether spec *prose* should be walked at all is deliberately left as it is: the
   check walks the whole JSON on purpose, because narrowing it is how a prose string
   later becomes a drawn string that nobody re-checked. `--strict` is the switch for
   anyone who wants the 24 treated as failures.

The suite's `05-assets.cmd` phase is green today on the strength of that split:
class 1/2/3 all ok, informational counted and printed.

## 4. What the host phase does and does not cover

`tools/suite/05-assets.cmd` runs, in order: the generator's `--check`, the real
`badge_assets.c` + `badge_assets_data.c` compiled and run against
`tests/host/test_badge_assets.c` (clang/mingw, `-std=c11 -O2 -Wall -Wextra
-Werror`), the same two generated files under `xtensa-esp32s3-elf-gcc` with the
firmware's own flag set, and finally the font coverage check.

Not covered, deliberately:

* the four vendored font files are **not** compiled on the host. They need the
  real LVGL headers (`lv_font_fmt_txt_dsc_t`, `LV_FONT_FMT_TXT_CMAP_*`, ...) plus
  `lv_conf.h` from the build directory; a stub broad enough to compile them would
  be a fake LVGL that tests could pass against. They are checked instead by
  `check-font-coverage.mjs`, which parses their cmaps directly, and by the
  one-off xtensa probe described in 1a.
* the xtensa step compiles only `badge_assets.c` and `badge_assets_data.c`.
  `badge_spec_data.c` and `badge_geom.c` already have their own xtensa steps in
  `00-spec.cmd` and `01-geometry.cmd`, and the host compile in step 2 already
  covers both of them at `-Werror`.
* `HOST_FW_GCC` **is** exported by `tools/run-host-tests.cmd` today (it sets both
  `FIRMWARE_GCC` and `HOST_FW_GCC`), so step 3 runs; the phase also falls back to
  `ESP_IDF_XTENSA_GCC` and then the default ESP-IDF path, and skips loudly if none
  of them exists.
* the icons and sounds are not compared against the reference renderer's output;
  `tests/host/test_badge_assets.c` proves they are present, non-degenerate and
  self-consistent, not that a given icon looks right. `icons/_图标总览.png` is the
  package's own contact sheet if a human wants to eyeball that.
* `bolt` is now in the index, so every package icon has a slot -- but *having a
  slot* is not the same as *being drawn*: `badge_paint_battery()` is what would put
  it on the glass, and no spec element names it (see 2a).

### 4a. The PNG decoder is cross-checked against Pillow, once

A decoder that reads the wrong row still produces a plausible 16x16 icon and still
passes every check in `test_badge_assets.c`; the first version of
`tools/gen-badge-assets.mjs` did exactly that (it added `y * stride` to an already
absolute bit index, so row *n* was filled from row *n+1* and the last row read past
the buffer). It was found by decoding all 28 package icons with Pillow and diffing
the emitted `badge_icon_*_data[]` arrays byte for byte:

```
28 emitted icons compared against Pillow, 0 mismatched
```

(That run predates `bolt` being registered in the index; with the icon now in
`badge_icon_names[]` the expected line is 28.)

That diff was a throwaway script, so here is the recipe (Pillow is in this
workspace's bundled Python; the comparison must parse the generated C, not
re-implement the decoder):

```python
# build/pil_icons.json <- Pillow's own decode of every package icon
import json, os, sys
sys.path.insert(0, r"<bundled-python>/Lib/site-packages")
from PIL import Image
ICONS = os.path.join("_ref", "baji-spec", "\u5427\u5527\u4ea4\u4e92\u89c4\u8303", "icons")
out = {}
for n in sorted(os.listdir(ICONS)):
    if n.endswith(".png") and not n.endswith("@3x.png") and not n.startswith("_"):
        im = Image.open(os.path.join(ICONS, n)).convert("RGBA")
        out[n[:-4]] = [list(p) for p in im.getdata()]
json.dump(out, open("build/pil_icons.json", "w"))
```

```js
// then, for each name: parse badge_icon_<name>_data[16*16*4] out of
// main/ui/badge_assets_data.c and compare vals[i*4+ch] against pil[name][i][ch].
// Expected: "27 emitted icons compared against Pillow, 0 mismatched" and no
// array for bolt (it is in no index).
```

The vendored sounds are cross-checked the other way round, and permanently: the
