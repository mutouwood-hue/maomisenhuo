# 差距报告：固件 vs 原型 v1.3（`小橘电子宠物.html`）

这份文档回答一个问题：**以 Notion 上现版原型为尺子，板端固件实现到哪一步了。**

它存在的理由和 `porting-notes.md` 类似，但方向相反。那份文档记录"规则怎么从原型搬到板端"；这份记录"原型往前走了、板端没跟上的部分"。两者必须分开写：把"欠账清单"混进"移植出处表"，会让出处表看起来像一份未完成的工作计划，也会让后来的人分不清哪条是**已验证的规则**、哪条是**待实现的功能**。

## 0. 结论摘要

| 层 | 状态 | 一句话 |
|---|---|---|
| 玩法内核数值 | ✅ **逐值一致** | 衰减、互动、诊所、成长、目标、户外、道具、服饰价格、品种全部与新原型相同 |
| 3D 渲染 | ⚠️ **另一条技术路线** | 自研可用且有测试，但与原型交付的 PCAT 管线是两套体系 |
| 服饰（衣柜） | ⚠️ **数据有、渲染无** | 6 款服饰在 `pet_state.c` 里，`cat3d` 完全不知道它们存在 |
| 新原型新增的玩法层 | ❌ **整体缺失** | 毕业、配对育幼、委托、手记、怪行为、偶遇、掉落节点 |
| 生活同步 / 时间环 / 语音 | ❌ **整体缺失** | 原型（App 侧）已实现，板端零实现 |
| 近场社交 BLE | ✅ **板端超集** | 原型是纯单机，这一层板端是新增，无原型可对照 |
| 功耗 / 四档模式 / IMU | ❌ **零实现** | 与文档 §9.2 的 TBD 一致 |
| 离线下降 / 环境感知 / 步数 | ✅ **不是欠账** | 原型自己也没实现（见 §4） |

内核没跑偏是重要的好消息；坏消息是**玩法层整体落后了一代**。只看板端代码和仓里的旧文档，会以为"只差功耗和语音"；对着现版原型看，缺的是毕业、繁育、委托、手记、怪行为这一整层。

## 3. 渲染层：两条不同的技术路线

原型交付了 **PCAT v1** 资产管线（`_ref/notion/吧唧渲染工具包.zip`），它是**实物而非纸面设计**：

| 交付物 | 体量 | 内容 |
|---|---:|---|
| `out/pixelcat.pcat` | **205,624 B** | 块结构 HEAD 14 / BONE 326 / CUBE 3,138 / OUTF 508 / ANIM 4,727 / TEX4 196,854 |
| `out/pixelcat_asset.h` | 1,054,194 B | 同一份数据的 C 数组，可编入 Flash 走 XIP |
| `ref.js` | 19,361 B | 按 C 写法实现的参考渲染器，供"逐函数对照移植" |
| `pcat-export.mjs` | 10,729 B | `.bbmodel` → PCAT 导出器（依赖 sharp） |

PCAT 管线的特征（`ref.js`，`SCR=466, STRIP_H=32`）：条带光栅化 + **16 位深度缓冲** + 定点 28.4 边函数 + **透视校正 UV** + **4bpp 调色板贴图** + 16 级光照 LUT + 脏矩形送屏；`OUTF` 块内含 **6 款服饰的纯色方块**，`ref.js` 有 `setOutfit()`。

板端现状（`components/cat3d/`）：`cat_model.h`(93,515 B) + 6×131,072 B **原始 RGB565** 贴图（共 **786,432 B**，目录 880 KB）；正交投影（**刻意去掉透视除法**）、**无深度缓冲**（画家算法 + 插入排序）、16.16 定点最近邻取样、32 级 Lambert、品红透明键。

| 维度 | 原型 PCAT | 板端 cat3d |
|---|---|---|
| 资产 | 205,624 B，6×32 KB 4bpp（可只载当前花色） | 880 KB，6×128 KB RGB565 |
| 深度 | 16 位 z-buffer | 无，画家算法 |
| 投影 | 透视校正 | 正交（有意） |
| 光照 | 16 级 LUT | 32 级 |
| 服饰 | `OUTF` 块 + `setOutfit()` | **无接口** |
| 分辨率 | 466 全屏 / 233 半分辨率 | 300×300 LVGL 画布 |
| 内存 | 条带缓冲 466×32×2B ×2 + 深度条带 | 300×300×2 = 180 KB 全帧 PSRAM |

**两套体系无法逐函数对照**，`ref.js` 的价值目前用不上。这不是"文档写了没做"，而是**交付物已经就位、板端走了另一条路**。

> **这个决定已经做了**：结论是**继续自研 `cat3d`、否决把 PCAT 作为固件渲染路线**，理由与全部量化对比见 **`docs/render-route.md`**。三点必须一并记住，否则会误引本节的表格：
>
> 1. 上表"资产 880 KB vs 205 KB"是 **flash** 字节之差，不是内存之差。贴图经 `EMBED_FILES` 走 XIP 读 flash，占 0 字节 SRAM；真实常驻内存两边**大致相当**（≈200 KB vs ≈187 KB）。
> 2. `partitions.csv` 给了 8 MB 的 `factory` 分区，880 KB 约占 10%，所以 **flash 不是本项目的约束**——PCAT 唯一确定的实质优势不落在约束上。
> 3. 唯一还站得住的 PCAT 技术优势是 **16 位 z-buffer**，它指向 cat3d 一个**未验证的失效模式**：加服饰方块后画家算法可能给出可见的前后排序错误，而 **golden 测试永远发现不了**（其参考实现 `tools/firmware-ref.mjs` 用的是同一个画家算法与同样的平均深度排序，两者会同错）。`docs/render-route.md` §6.1 给出了翻案触发条件。

工具包里还给了成本模型与两个方案的估算（466 全屏约 31–33 fps / 233 半分辨率约 90 fps，30 fps 时 CPU 约 90% vs 26%），并建议互动档用半分辨率。板端目前是自适应：`CAT_VIEW_MIN_FPS 12`、占空比 3/5。

## 4. 明确**不算欠账**的项（文档说"已完成"、原型其实也没做）

这几条很重要：如果不写下来，下一轮又会把它们当成固件的缺口去填。

| 项 | 事实 | 取证 |
|---|---|---|
| **离线下降**（1/4 速、下限 20） | 原型**完全未实现**。唯一 tick 是 `Math.min(2,(i-ec)/1e3)`，且 `document.hidden` 时**整帧跳过**；`lastSavedAt` 只写不读 | `@1,178,980`；`Q(C)` 自身再夹 `Math.min(30,C)` |
| **环境感知** | 原型开关 `disabled`，文案写明`原型不实现`，内容是硬编码 5 行假数据，`cfg.scene` **零读取** | `#5/L703`、`#5/L740` |
| **运动与步数** | 同样 `disabled`；`DeviceMotion`/`Accelerometer`/`stepCount` **0 命中**，步数是合成数 | `realDay` 返回 `steps:null` |
| **"全部默认关闭"** | 实际默认 `demo:true`，只有其余为 false | `#5/L407` |

板端与原型在"离线不惩罚"上**行为一致**：原型只有静态文案承诺`离线不会扣状态`（`@58,892`、`@64,027`），板端则用 30 秒单步钳制实现。

同理，**近场社交不是欠账而是超集**：原型的"配对对象"是本地 NPC `小伙伴`，全文 `bluetooth` **0 命中**；板端的 `net_link`/`net_social` 是纯新增 M1 工作。原型里的"偶遇"（户外随机事件）与板端的"遇见"（BLE 握手）**是两个不同的东西**，别混淆。

## 5. 原型内部的已知问题（实现前要先知道）

原型的这些不一致会影响板端怎么实现，**建议先反馈给文档侧**再动手：

1. **语音意图 6 类与文档不符**。实际是：到家 / 吃饭 / 晚安 / 累了 / 夸夸 / **出门**。文档写的"想你"和"叫名字"**没有对应类别**——叫它名字会落到通用的`❓喵？（歪头）我听到你啦。`（权重 1）。
2. **「保存在本机、不上传」与 OSM 瓦片矛盾**。真实地点会默认拉 `https://tile.openstreetmap.org/16/{x}/{y}.png`（`cfg.tiles` 未定义 → 默认为开），且该开关**未暴露在隐私页**。这是合规风险，不能对外按"不上传"表述。
3. **吧唧"通过蓝牙同步"是纯文案**：`bluetooth` **0 命中**，吧唧只是基于页面内 `day()` 数据的 240×240 canvas 预览。
4. **清除生活数据不彻底**：清了 `pg-life-geo/mom/names/claim/cfg`，但 `pg-quirks-v1`（怪行为图鉴）、`pet-ana-*`（埋点队列）、`pet-grad-photo:*`（毕业照）都保留。
5. **幼猫出生不继承**：`claimBaby` 走普通工厂 → `generation:1, heritage:null`；**只有毕业**才写 `generation+1`/`heritage`。所以"家风传承"在两代之间会静默断掉。
6. **毕业天数不可在页面配置**：`globalThis.PET_GRAD_ADULT_DAYS??7` 只读（注释写"可在页面顶部改"= 改源码）；`TRIAL_DAY=14` 是硬 `const`。
7. **偶遇是确定性的**：`hash(sessionToken) % 3`，一次出门一次；玩家不理会在 1.5 秒后自动选 `safe`。雨衣减伤是**装备门控**（雨衣 −2 / 无雨衣 −18 且感冒），不是随机。
8. **时间环是"单日"模型**：`day.segs = [{start,end,kind,place}]`，**分钟偏移 0..1440**，无小时分桶、无多日存储（moments 按 7 天/300 条裁剪）。**别按"24 个小时格"设计板端数据结构。**

### 6.1 关于缺陷 1 的补充：只接 `flush()` 是不够的

修这个缺陷时发现原始描述低估了它。`pet_save_touch()` 只是**标记并延迟**：它只在**再次被调用且已过 5 秒**时才真正写盘。设备上没有任何定时器执行那次延迟写，而徽章靠电池供电、**没有可靠的关机时刻**（`pet_save.h` 原先写的"用于关机"在固件里根本没有对应钩子，`net_social.h` 也没有断链回调）。所以真实的失败场景不是"关机没落盘"，而是：

> 喂一次猫 → 再没有下一次 `touch()` → 这次改动**永远留在 RAM 里**

只有"再喂一次并等过 5 秒"才会顺带把它写下去。修法因此是两件：把 `poll` 挂到已有的 50 Hz 心跳上（`main.c` 的 `app_tick_cb`），让延迟写最迟在窗口结束时落盘；`flush()` 作为真正的会话结束钩子保留（重启前、UI 重启前）。同时修掉一个更隐蔽的缺陷：**原实现无论写盘成功与否都清除 pending 标志**，于是写失败被当成写成功，改动既不重试也不落盘。见 `pet_save.c` 的 `write_pending()`。

## 9. 待定：时间环需要的时间基础设施

生活同步与 24 小时时间环（§2）板上完全没有落点，而**原型本身不含任何在无网络硬件上取时间的方法**。方向上：

- **在无网络徽章上取时间**：DS3231 之类带温度补偿的 RTC 模块，或由手机 App 通过 BLE 下发时间。
- **需要判断**：多加一颗 RTC 的 BOM/功耗成本，是否比"仅在 BLE 连上 App 时才显示时间环"更值；以及没有 RTC 时页面该显示什么（原型是**单日**模型，见 §5 第 8 条，没有历史可回放）。
- 另外 `sdkconfig` 实测为 `# CONFIG_PM_ENABLE is not set`，即连 `esp_sleep` 的时基都还没启用，所以四档工作模式与时间环共用同一块前置工作。

这一项**建议在动玩法层之前定**，因为它决定数据模型（是否有可靠的小时时间轴）。
